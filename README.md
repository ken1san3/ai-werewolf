# AI Werewolf

複数のローカルLLMエージェントが、リアルタイムの自由会話で議論・推理・騙り・投票・夜の能力使用を行う**人狼ゲーム基盤**です。

単に「LLMへ人狼のルールを説明して会話させる」のではなく、ゲームの状態・ルール・勝敗判定・秘密情報をサーバ側で管理し、AIはWebSocket経由のクライアントとして参加します。  
そのため、AIが誤った出力をしてもゲームルールそのものは壊れず、各AIが知ってよい情報もサーバ側で制御できます。

現在は動作確認と比較評価のため**標準9人構成**を中心に実ゲームを行っていますが、AIの人数や役職構成を9人に固定した設計ではありません。

> 個人開発プロジェクトです。開発開始は2026-08-29。  
> 元のPrivateリポジトリでの開発履歴452 commits（2026-08-29〜2026-10-06、全ブランチ・タグ）を、日時を維持したまま引き継いだ公開版です。公開準備のcommitは別に追加しています。
>
> 人狼のルールは「人狼ジャッジメント」（そらいろ株式会社）の公式ヘルプを調査して設計の参考にしました。  
> 本プロジェクトは非公式であり、同社とは関係ありません。設計への反映内容は [参照ルールの調査と設計への反映](Docs/ai/spec/JUDGMENT_REFERENCE.md) にまとめています。

## なぜ作ったか

もともと人狼ゲームが好きで、LLM同士が自由に議論・推理・騙りを行ったとき、どこまでゲームとして成立するのかに興味がありました。

以前は複数のLLMを同時に扱うには大きな計算資源が必要だと考えていましたが、手元の**8GB VRAMのGPUでも動作するローカルLLM**が登場していることを知り、「自分のPCでも複数AIによる人狼を実現できるのではないか」と考えて開発を始めました。

人狼は、LLMエージェントを試す題材としても次の特徴があります。

- プレイヤーごとに知ってよい情報が異なる
- 嘘や役職の騙りがゲーム上の正当な戦略になる
- 発言順が固定されず、他人の発言への反応が必要
- 会話だけでなく、投票・能力使用・勝敗判定といった明確なルールがある

そのため、**秘密情報の扱い、複数AIのリアルタイム会話、誤った出力への耐性、会話品質の評価**を、実際に動くシステムの中で検証できると考えました。

## 何を実装したか

| 部分 | 内容 |
|---|---|
| ゲームコア | フェーズ進行、投票、夜の能力使用、死亡、勝敗判定、イベント記録 |
| ネットワークサーバ | WebSocket接続、再接続、公開・非公開イベントの配送、AIからの要求の検証 |
| 通信プロトコル | JSON Schemaで定義したバージョン付きメッセージ |
| 役職・ルール定義 | 13種類の役職、陣営、能力、ルールをYAMLで定義 |
| AIエージェント | 発言するかの判断、発話生成、反復抑止、行動要求、実行記録 |
| 評価・実験基盤 | 会話品質、秘密情報漏洩、サーバ拒否、クラッシュなどの自動確認と複数モデル比較 |
| リプレイ | 公開情報だけから自己完結HTMLを生成し、試合一覧・検索・再生速度変更に対応 |

主な使用技術は **Python / WebSocket / JSON Schema / YAML / pytest / GitHub Actions / llama.cpp** です。  
リプレイ画面はHTML/CSS/JavaScriptで生成しています。

## 技術的に難しかったことと解決方法

### 1. LLMの誤りでゲームルールを壊さない

LLMは、存在しないプレイヤーへの投票や、現在は使えない能力の使用など、不正な要求を出す可能性があります。

そこで、ゲーム状態・フェーズ・能力の可否・勝敗を**サーバだけが決定するサーバ権威型**にしました。AIからの要求はすべて現在のゲーム状態と照合し、不正な要求は理由付きで拒否します。

ゲームコアはLLMに依存しないため、AIを使わずにルール部分だけを単体・結合テストできます。

### 2. 秘密情報をAIごとに分離する

人狼の仲間情報、占い結果、霊能結果、秘密チャットなどは、プレイヤーごとに見えてよい範囲が異なります。

プロンプトに「秘密を話さないで」と指示するだけではなく、**知る必要のない情報をサーバからそのAIへ送らない**設計にしました。公開イベントと非公開イベントはネットワーク配送の段階で分離しています。

公開用リプレイも同じ考え方で、公開イベントだけを許可リスト方式で書き出しています。

### 3. 1台の8GB VRAM環境で複数AIをリアルタイムに動かす

各AIが順番に1回ずつ発言する方式ではなく、各エージェントが「今発言するべきか」を判断する自由会話にしています。

一方で、開発環境では1つのLLMサーバを複数エージェントで共有するため、生成中にゲーム状況が変化することがあります。  
そのため、生成後に状況が古くなっていないか確認し、すでに意味を失った発言は送信せず破棄する仕組みを入れています。

現在の主な検証構成はRTX 3070 Ti 8GB + ローカルLLMです。

### 4. 役職追加のたびにゲームコアを書き換えない

「村人陣営か人狼陣営か」だけでは、狂人や妖狐のような特殊な役職を表現できません。

そこで役職を、

- 勝利する陣営
- 勝敗判定上どちらの人数として数えるか
- 人狼に襲撃されたときの結果
- 占われたときの結果
- 霊能されたときの結果

などの独立した属性に分解し、YAMLで定義しています。

これにより、ゲームコア側で「この役職名なら特別処理」といった分岐を極力持たずに13種類の役職を表現しています。

### 5. 「会話品質の改善」が逆に開発を止めた

開発中、会話品質を数値化するための評価指標や合成テストを増やし続けた結果、**約2週間、実際のゲームを1回も回さない状態**になりました。

Git履歴、生ログ、同じモデルでの再実行から原因を調べたところ、主に次の問題が見つかりました。

- 「他人の発言に反応したか」をモデル自身の出力ラベルで評価しており、実際には反論していても失敗扱いになることがあった
- コンテキスト長の見積りが不適切で、AIに渡る会話履歴が必要以上に削られていた
- 合成テストの合格を重視しすぎ、実ゲームでしか分からない問題を確認できていなかった

そこで、検証済みだったゲームコア・サーバ・通信部分は残し、AI側と評価方法を再構築しました。  
再構築後は、標準9人構成で実ゲームを繰り返しながら改善する方法へ変更しています。

詳しい原因分析と再現方法は [Docs/analysis/2026-10-02/FINDINGS.md](Docs/analysis/2026-10-02/FINDINGS.md) に残しています。

## システム構成

~~~text
┌─────────────────────────────────────┐
│ Werewolf Server                     │
│                                     │
│ ゲーム状態・ルール・勝敗を管理     │
│ AIからの要求を検証                  │
│ 公開情報 / 秘密情報を配送し分ける   │
└─────────────────┬───────────────────┘
                  │ WebSocket + JSON
                  │ JSON Schemaで検証
          ┌───────┼────────┐
          │       │        │
      AI Agent  AI Agent  AI Agent ...   ← 人数は固定しない
          │       │        │
          └───────┼────────┘
                  │
             LLM Server
              llama.cpp
                  │
        Local LLM (Qwen / Gemmaなど)

現在の主な評価構成: 標準9人
~~~

AIエージェントはゲームサーバ内部の状態を直接参照せず、WebSocketで受け取った情報だけを使って判断します。

## テスト

pytestが収集するテストは **388件（809 subtests）** です。  
実LLMを必要とするゲーム評価はCIには含めず、ゲームコア・通信・AIエージェントの制御部分などは偽のLLMを使って自動テストしています。

公開準備時点の結果:

| 環境 | 結果 |
|---|---|
| GitHub Actions | Ubuntu（Python 3.10〜3.13）・Windows（Python 3.13）の全ジョブ成功 |
| Linux / Python 3.14 | 387 passed / 1 skipped / 809 subtests passed |

テストには、サーバと複数クライアントを接続して1ゲームを最後まで進めるテストや、公開サンプル4試合からリプレイHTMLを再生成し、コミット済みHTMLと一致することを確認するテストも含まれます。

## 実行方法

### テスト

~~~bash
python -m pip install -e ".[dev]"
python -m pytest -q
~~~

### ローカルLLMでゲームを実行

OpenAI互換APIを持つ [llama.cpp](https://github.com/ggml-org/llama.cpp) の `llama-server` を起動します。

開発ではQwen3.5-9B Q4_K_M、コンテキスト8192を主に使用しています。

~~~bash
llama-server -m <path-to-model>.gguf --host 127.0.0.1 --port 8090 -c 8192 -np 1 --jinja --reasoning off -ngl 99
~~~

別のターミナルからゲームを開始します。

~~~bash
python -m ai_agent.play --seed 1
~~~

実行結果は `games/` 以下に保存され、会話の書き起こしと自動チェック結果を確認できます。

### 公開リプレイを再生成

~~~bash
python -m ai_agent.replay --root samples --output samples/html
~~~

## AI支援開発について

このプロジェクトでは、Codex（OpenAI）とClaude（Anthropic）を開発支援に使用しています。

**作者が担当していること**

- 何を作るか、どのルールを採用するかの決定
- システムの設計原則
- 評価指標と合格条件の設定
- 実ゲームの結果確認
- 改善案を採用するか、戻すか、再構築するかの判断

**AIツールに任せていること**

- Codex: 主に実装、テスト、ゲーム実行、記録
- Claude: 主にレビュー、設計や実装の確認、原因分析
- ローカルLLM: 2026年9月上旬に開発補助として試行し、その後廃止

設計判断、作業記録、レビューの経緯、AI共同作成を示すcommit情報はリポジトリ内に残しています。  
AIの利用を隠すのではなく、**人間が何を判断し、AIをどこに使ったかが追えること**を重視しています。

## 既知の課題

- AIが自分の役職や他人の発言内容を取り違えることがまだある
- 会話品質の一部は機械判定だけでは評価しきれず、人間による確認が必要
- ゲーム後に生成した改善ルールの自動評価が基準未達で、長時間比較実験は保留中
- 実時間で進む一部のテストは、ローカルPCが高負荷のときタイムアウトすることがある
- 長時間のモデル比較ランナーは現在Windows向け
- 人間プレイヤー用UI、別PCへのAI分散、再接続の本格運用は未実装
