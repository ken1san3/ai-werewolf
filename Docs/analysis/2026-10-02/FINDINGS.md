## 2. 間違っていた前提

1. 応答できたかは、モデルの自己申告ラベルで分かる → 測定器の欠陥を会話品質の問題と取り違えた。
2. LLMは縛って検証すべき部品 → 9Bモデルに巨大なJSONを1回で出させ、「形式は正しいが中身が無い」出力（NONE、空欄）に収束させた。
3. 実ゲームの前に合成テストで完璧を示す → 合成ケースは履歴1〜3件で、履歴不足・反復・会話の流れを測れない。ゲートはユーザーの完了条件（各1件以上）より厳しかった。
4. 証拠の完全性と独立性が前進の条件 → 証明すること自体が仕事になった。
5. 各セッションは正本と指定範囲だけを読む → 生ログに戻って前提を見直す機会が仕組みとして無かった。

過去の分析（Claude によるものを含む）も同じ枠の中で行われ、これらの前提を引き継いでいた。
「普通の文章だけで指示する」という一番単純な比較は 9/19 に提案されていたが、実施されていなかった。

## 3. 再現実験（同じモデル Qwen3.5-9B Q4_K_M、同じ llama.cpp build 10697）

| 実験 | 結果 |
|---|---|
| E1 保存プロンプトを製品と同じ形で再送 | ログとほぼ同じ出力（環境の再現を確認） |
| E2 省かれた履歴を戻して再送 | 改善しなかった（自分の前の発言の丸写しが増えた）。履歴不足は欠陥だが主因ではない |
| E3 同じ局面・同じ情報で普通の文章のプロンプト＋自由文 | 0.6〜1.7秒/発言。自己紹介なし、名指しの質問と反論、狼は否定・偽装 |
| E4 普通の文章だけの最小9人ゲーム×5（サーバなしの模擬） | 全回完走。狼側の自白0、自己紹介0 |
| E5 発話の種類のラベルを生成後に別の小さな呼び出しで付与 | 同じモデルが NONE 0件で妥当なラベルを付けた（T401 の製品ログにも反論5・回答2） |
| 実サーバでの試作（`spike/`） | 実サーバに9人をリアルタイム接続して3ゲーム完走、サーバ拒否0、生成1.3〜2秒、待ち中央値約2.5秒 |

実サーバ試作で見えた本当の課題: 初日の空の同意（初版42%）、死者への呼びかけ（初版60%）、
ゲームの仕組みの誤解（初日の占い結果、霊媒の能力）、事実の取り違え。
プロンプトを1回直し同じseedで回すと、死者への呼びかけ60%→3%、空の同意11%→2%（各1ゲームの比較で目安）。

## 4. 手戻りの判断

- 残す: ゲーム本体・サーバ・プロトコル・役職データ（旧 Phase 1〜2）。テストは削除後のツリーで 204 passed。
- 作り直す: AIの判断・発話部分（旧 Phase 3.3〜6）と開発の進め方。
- 土台: `main`（5a5635f）。experimentブランチは持ち込まず、タグで保存。
- 詳細な一覧: `rebuild/REBUILD_MANIFEST.md` と `rebuild/rebuild_manifest_main_5a5635f.tsv`。

他エージェントの方針書（評価・実験経路だけを作り直し、現v2を測ってから部分置換、実ゲームは最後）は採らない。
理由: 「先にオフラインで証明する」という停滞の前提と同じ形で、v2・発言制御・GPU待ち行列管理を残すと
「1日2回まで」「到着順」「12項目JSONとの結合」も残るため。
取り入れた指摘: 自由会話を順番制にしない、自分の結果の公表と漏洩を分ける、合法な騙りと証拠の捏造を分ける、
新しい形式やゲートは防ぐ誤りを一文で言える場合だけ、旧資料は消さずに保管。
