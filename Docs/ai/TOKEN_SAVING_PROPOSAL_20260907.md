## 推奨構成

節約対象は主にGPT/Claudeの消費。成功した開発タスクあたりの消費を最小化する。
スクリプトで抽出・検証し、Qwenで通常の調査・下書き・実装・修正、Sol/Claudeで重要判断を行う。
Geminiは標準工程に含めず、具体的な必要性がある場合にのみ使う。
工程の進行、再試行、ログ回収のために上位モデルを常駐させない。

| 担当 | 主な仕事 | 任せない判断 |
|---|---|---|
| Python等 | ファイル・差分・テスト結果の抽出、契約形式検証、実行制御、証拠保存 | 意味的な仕様判断 |
| Gemini Pro | 他の3モデルへ任せる合理性が低い大量資料の整理・横断調査など、例外的な補助 | 通常工程の必須担当、最終設計、承認、調査漏れなしの保証 |
| ローカルQwen | 通常調査、契約・文書草稿、確定契約の実装、失敗ログに基づく修正、Yellowの独立コンテキストレビュー | 仕様変更、自己申告による合格、難しいキャンセル処理の単独実装 |
| Sol | 新しい不変条件・API・状態遷移の設計、契約確定、高リスク最終確認 | 日常的なrunner進行管理 |
| Claude | 現行規則によるSol作成設計の独立承認、Hard Redの独立レビュー | 毎回のログ整理 |

モデル割当の変更は別途正式な運用改定が必要。現行D051/D053の承認要件は維持する。

## 添付評価から採用できること

- Green: Fine SoloもFine PipelineもFinal完全Pass 90%。通常は単独実装でよい。
- single_source_medium: Fine SoloのFinal 100%に対しPipeline 70%。自動的にReviewer/Fixerを追加しない。
- Yellow: Fine Pipelineは85% blind、97.5% final。限定された分業は有望。
- cancellation-resistant Brain: Fine Pipelineでも40%。ここは上位モデルへ残す。
- 細かい契約は成功率だけでなくrunner所要時間も改善した。曖昧な短い指示に戻す節約は避ける。

528セルは12課題の反復を含む。実リポジトリの成功率・削減率への外挿はできない。
Finalはhidden失敗ログを返した後の値で、未知不具合への検出力を意味しない。
契約作成に必要な上位モデル消費も未計測で、これを含めて初めて費用対効果を判断できる。

## Geminiの使い方

通常の調査・契約草稿はQwenが担当する。Geminiは消極的な補助とする。
呼出前に、スクリプトで済まないか、Qwenで十分でないか、上位モデルの重要判断なのかを確認する。
大量資料の整理や広範な候補探索でQwenの実装処理を長時間占有し、GPT/Claudeの消費も大きくなる場合などに限って候補とする。
別の必要性は、その環境で他の3モデルにない入力・アクセス能力が確認できた場合。Geminiが必ず優れているとは仮定しない。
Qwenが難しいコードを解けなかった場合の標準昇格先はGPT/Claudeであり、Geminiではない。
呼出理由を短く記録し、Geminiがなくても通常開発が完了する構造にする。
使う場合も、全体理解を丸投げせず、証拠で検証できる問いに分ける。

出力項目を次に固定する:

1. 調べたファイル一覧と版・ハッシュ
2. 事実ごとのファイルパス、シンボル、行番号、短い原文
3. 事実と推測の区別
4. 不明点と未調査範囲
5. 上位モデルの判断が必要な論点

パスや引用の存在はスクリプトで検査する。意味の正しさまでは機械検査だけでは保証しない。
上位モデルは重要な判断箇所と関連境界の原文を確認する。
レビュー対象全体の一覧を保持し、Geminiが挙げなかった箇所を自動的に安全扱いしない。
現行のレビュー対象範囲を要約だけで削らない。

Geminiの繰り返し多数決は採らない。同じ見落としを反復する可能性がある。
追加呼出しは「未確認の呼出元を調べる」等、異なる具体的な問いに限る。
Qwen ResearcherとGemini Researcherを同一調査に常時二重投入しない。

具体的な利用機会が生じた時点で、ユーザーの契約で利用できる受渡し経路を確認する。
契約内で使えることと、runnerから自動API呼出しできることは別に確認する。
自動接続を前提に初期投資しない。

## 契約と文脈の再利用

最重要は「毎回Solが長いFine Contractを新規作成する」を避けること。
承認済み設計から実装契約を抽出し、共通不変条件・API・受入条件を再利用する。
Qwenは草稿を埋め、Solは新規判断、差分、矛盾、未確定箇所を確認する。
小タスクでも版に対応した必要な契約本文をQwenへ渡す。参照IDだけでは不足する。

契約には最低限、目的、許可ファイル、対象外、API/型、状態遷移、不変条件、エラー処理、受入条件、必須テスト、禁止事項、完了証拠を含める。
並行処理がある場合は所有者・cancel・await・timeoutの意味も確定する。
上位モデルの設計承認を省略する根拠にはしない。

ファイル一覧・import関係・既存契約は機械抽出を優先する。
現在状態、対象設計、対象差分、未解決事項だけで次セッションを再開可能にする。
設計・入力ファイルのハッシュが変わったときだけ対応する調査・契約の再確認を行う。
失敗時は失敗テストの原文、関係するコード、変更差分を渡す。全成功ログの再送は不要。
件数・成否はexit codeと生の最終行、構造化テスト結果を根拠とする。

## リスク経路の提案

| 区分 | 経路 |
|---|---|
| Green | 承認済み契約の具体化 → Qwen実装 → 機械検証 → 失敗時だけ修正 |
| Yellow | 契約確定 → 必要な調査 → Qwen実装 → 機械検証 → fresh Qwenレビュー → 具体的違反だけ修正 |
| Red | Solが状態・所有権まで確定 → Qwen実装と検証 → Sol最終確認 |
| Hard Red | Sol/Claude等の上位モデルが主担当 → 別の上位モデルで独立レビュー |

処理名だけでGreenに分類しない。決定的なresolverでも秘匿情報・権限・勝敗に影響すれば高リスクになり得る。
リスク不明、範囲拡張、新しい設計判断が必要な場合は上位へ戻す。
同じ失敗の修正は最大2回を暫定上限とし、契約不足ならその前に戻す。
スタイル改善案だけでFixerを起動しない。

これらは移行後の候補経路である。現行の承認・レビュー義務を今回変更しない。
特にGreenでも「機械テスト合格」と「仕様整合・正式完了承認」を区別する。

## 今週の基盤投資

今週1週間分のトークンを基盤開発に投資できる。少数試行後までrunner整備を先送りする前案を改め、日常運用に必要な基盤を今週の投資対象にする。
週予算は消費許可であり、使い切り目標ではない。具体的トークン数、追加購入、翌週以降の継続実行は仮定しない。
優先する実装候補:

1. 契約と固定入力の受渡し
2. Qwenの構造化whole-file出力の検証と隔離領域への適用
3. テスト実行と生の証拠保存
4. 最大2回の修正、解決しない場合の引継ぎ
5. モデル別usageと結果の記録
6. 中断後の再開、入力変更検知、二重適用防止、変更候補の安全な取消し
7. リスク別の担当選択、契約再利用、上位へ必要情報だけを渡す引継ぎ
8. ai_status等の既存入口への統合とQwen中心の日常運用文書

推奨予算配分は、移行設計と独立レビュー20%、runnerと編集制御35%、検証と障害試験25%、実タスク試行と運用統合15%、修正予備5%。これは配分案であり実測消費ではない。
最初に全体契約を固め、機能を分割して実装・検証する。汎用GUI、多数のprovider連携、常時多agent化、Gemini自動接続は今週の優先対象にしない。
基盤自体の変更適用・隔離・再開・プロセス終了処理は影響が大きいため、GPT/Claudeへ設計・検証の投資を惜しまない。決定済みの限定部分はQwenで実装する。

既存通信ライブラリの再利用は、実装前の対象限定調査で確認する。
whole-file方式は評価資料に根拠があるが、大きな既存ファイルでは欠落を監視する。
runnerが元ファイルのハッシュ、許可範囲、削除量、生成差分を検査する。
Qwen自身がファイル数・テスト・検証ルールを勝手に変更できないようにする。
ローカルでは必要な全文を生成しても、上位へはrunnerが抽出した差分と必要な周辺コードを送れる。

テスト側と製品コード側が同じ誤解で一致しないよう、既存テストと契約由来の受入条件を保護する。
新規不具合テストは必要に応じbuggy版で失敗しfixed版で成功することを確認する。
worktree試験のimport混入という報告済み失敗を踏まえ、実行対象のmodule.__file__等も記録する。
修正中は対象テストから始め、候補確定時に必要な全回帰とcheck_docsを行う。
同じコードに対する不要な全回帰反復を避けるが、既存の必須検証は削らない。

## 導入順と効果測定

1. 現行Design Gateに従って移行設計・独立承認を行う。通常Qwen、例外Geminiの条件を固定する。
2. runner、編集制御、機械検証、再試行・再開、証拠保存を実装する。
3. 不正パス、古い入力、空出力、未収集テスト、import混入、途中停止を検証する。
4. 実際のGreen/Yellowタスクで一連の処理を試し、既存入口と運用文書へ統合する。
5. 対象タスク10件程度を初期評価単位として、消費・手戻り・時間を記録する。Red/Hard Redの上位確認を維持する。

10件は導入判断の初期材料であり、統計的な品質保証ではない。
モデルごとに入力・出力・取得可能な推論トークン、再試行数、上位介入回数、所要時間、レビュー後の欠陥を記録する。
usageが取得できない場合は推定を明記し、会話文字数を実トークンと呼ばない。
主指標は「GPT/Claude総消費 ÷ 受入完了タスク数」。難易度別に比較し、未完了・失敗に使った消費も含める。
基盤開発に使った消費も記録し、1タスクの削減量で割って回収に必要な件数を見積もる。
現時点で「何%削減できる」とは断定しない。
