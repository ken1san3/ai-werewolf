## A. マスター仕様 — Critical

### A-1. `team` が「勝利陣営」と「占い判定」を兼ねている

§7 / §9 / §31 では役職に `team` しか持たせていない。しかし:

| 役職 | 勝利陣営 | 占い判定 |
|---|---|---|
| 狂人 | wolf | 白（村） |
| 妖狐 | fox | 白（村） |
| 人狼 | wolf | 黒 |

`team` 一本で実装すると狂人が黒判定になる。§31は「狂人をどう判定するかは
ルール設定化できると望ましい」と書いてあるだけで、モデル上の解決策が無い。

§32 の抽象化リスト（Role/Team/Knowledge/Ability/Passive/Effect/WinCondition/
ChatPermission）にも `Alignment`（見え方）が欠けている。

→ **`team`（勝利）と `alignment`（判定上の見え方）を分離する。** OPEN_QUESTIONS Q1。

### A-2. 村の勝利条件が狂人で成立しない

§10 の村:

```yaml
win_conditions:
  - type: eliminate_team
    target: wolf
```

狂人が `team: wolf`（§31で明記）なので、**狂人が生き残っている限り村が勝てない**。
`eliminate_team` は実際には「襲撃能力を持つ役職の全滅」を意味している。

→ 勝利条件の対象を陣営ではなくタグ/役職集合にする。OPEN_QUESTIONS Q2。

## B. マスター仕様 — 仕様の抜け（Phase 1 で必要）

### B-1. ゲームルールの既定値が丸ごと未定義

以下は人狼で最も揉める部分だが、仕様に一切記述が無い。

```
初日処刑の有無
初日占い（自由 / ランダム白 / なし）
初夜襲撃の有無
投票同数時（決選投票 / ランダム / 処刑なし）
連続護衛の可否
狩人の自己護衛の可否
霊能結果の通知タイミング（当夜 / 翌朝）
複数狼の襲撃先決定（多数決 / 指定役 / ランダム）／同数時
```

「設定化する」とは書かれているが**既定値が無い**ため、実装者が勝手に決めると
後で全部やり直しになる。OPEN_QUESTIONS Q3。

### B-2. 勝敗判定のタイミングが未定義

§10 の `parity`（狼数 >= 村人数）を、処刑直後 / 襲撃直後 / 朝 のどこで評価するかで
最終日の結果が変わる。§6のイベント列に `GAME_END_CHECK` はあるが、
どのイベント後に発火するかが書かれていない。OPEN_QUESTIONS Q4。

### B-3. 行動未選択・タイムアウト時の既定挙動が無い

占い師・狩人・狼が時間内に対象を選ばなかった場合の扱いが未定義。
LLMは必ず失敗するので、Phase 1 の時点でサーバ側フォールバック
（ランダム / 不発 / 前回継続）が要る。OPEN_QUESTIONS Q5。

### B-4. §11 の解決順に「非解決系能力」が混ざっている

§7 の werewolf 定義で `wolf_chat` が `timing: night` の ability になっているが、
これは Effect を解決する能力ではなく ChatPermission である。
§32 が「AbilityとChatPermissionを分離せよ」と言っているのと矛盾する。

→ `wolf_chat` は ability ではなく `chat_channels: [public, wolf]` として持たせる。

## C. マスター仕様 — ネットワーク（Phase 2 で効いてくる）

### C-1. プロトコルにバージョンが無い

§4.2 の共通フィールドは `type / event_id / game_id / timestamp / payload`。
§28 で「将来 C++ / TypeScript / Rust クライアントが接続可能であること」と

§40 で「再接続」は将来候補扱いだが、`game.state_sync`
（自分が知ってよい現在状態のスナップショット）は
**遅れて接続したクライアント・観戦者・UI 起動時にも必要**で、

### C-3. 順序保証・欠落検出手段が無い

WebSocketは順序保証されるが、切断中に落ちたイベントの検出には連番が要る。
`seq` を入れておくとリプレイ（§25）とも整合する。

### C-4. ログの公開/秘匿分離が §27 と衝突しうる

§24 は「秘密チャット・AI内部判断・LLM入出力を全部保存」、
§27 は「秘匿情報を漏らすな」。同一ログファイルに書くと、
観戦UI・リプレイ・デバッグ共有の段階で漏れる。
`public` と `private` を最初からファイル分割する方針を明記した方がよい。

## 良い点（追加）

マスター仕様 §32 が「Role / Team / Knowledge / Ability / Passive / Effect /
WinCondition / ChatPermission を混同しない」と言っているのは方向として正しく、
参照実装の狂人 / 狂信者 / ささやく狂人がまさに

### H-8 [High] Effect一覧で「付与」と「置換」が混同されている

マスター仕様 §8.2 の Effect 候補一覧は

| 機構 | 例 | 内容 |
|---|---|---|
| Modifier（付与） | 恋人、狐憑き、手玉、呪い | 元の Role を保持して重なる |

# 追補3 2026-08-29 — 役職仕様の確定後

### 参照実装からの意図的な逸脱を1件記録した

猫又の処刑時道連れを**採用しない**（`decisions/D011`）。
`decisions/D004` は人狼ジャッジメントを参照実装と定めているが、
「そのままコピーはしない」とも書いてある。
逸脱は Decision として明示的に記録し、
参照実装準拠の挙動を content 側で再現できることを合格条件にした。

**Reviewer の推奨が2件却下されている。** どちらも妥当な却下である。

| 項目 | Reviewer推奨 | 採用 | 理由 |
|---|---|---|---|
| 賢狼の情報取得 | 襲撃先に選んだ時点 | **襲撃成功時のみ** | 役職騙りという設計意図に沿わない |
| 猫又の道連れ | 本家準拠＋ループ防止 | **道連れ死を除外** | 発火条件を絞れば防止機構が不要 |

Reviewer は実装容易性から推奨を出したが、
ゲームデザインの意図はユーザーが持っている。
**この判断分担は `AGENTS.md` の Roles のとおりで正しく機能している。**

### 残る設計上の注意

`decisions/D010` の「乗っ取る」という表現が、
将来 **賢狼が対象の役職そのものを取得する**能力を指す可能性がある。
その場合は Modifier（D008）ではなく Role Replacement に該当し、
Phase 8 の設計対象になる。
現時点では `InspectDeadRole` の結果を
Role Replacement の入力に使える形にしておくよう D010 へ記載した。

### H-15 [Medium] Passive が「条件 → 効果」を複数持てる必要がある

猫又は死因によって道連れの対象プールが変わる（`decisions/D011`）。

| 死因 | 対象プール |
|---|---|
| 襲撃 | 生存する人狼から1名 |
| 処刑 | 生存者全員から1名 |

Passive のスキーマを「条件1つ + 効果1つ」で設計すると、
猫又を1つの Passive で書けず、
「襲撃用猫又Passive」「処刑用猫又Passive」の2つに分ける羽目になる。
役職定義が死因の数だけ膨らむ。

→ `rules: [{when, target, ...}, ...]` のリスト構造にする。
単一ルールは要素数1のリストとして扱えば、他の役職の記述量は増えない。

これは猫又固有の都合ではなく、
「Aの場合はX、Bの場合はY」という Passive は今後も必ず出る。

### H-16 [High] 死因は秘匿情報である — 公開死因との分離が必要

`decisions/D012` の検討中に判明した、**情報漏洩に直結する問題**。

参照実装では、呪殺された妖狐は朝に「無残な死体」として表示され、
襲撃死と区別がつかない。区別できてしまうと、村側は
「呪殺が起きた＝占い師が本物で妖狐を引いた」と即座に確定でき、
妖狐と占い師の駆け引きが成立しなくなる。

マスター仕様 §24 は「死亡理由」をログ項目として挙げているが、
§27 の情報分離との関係が書かれていない。素直に実装すると、
死亡イベントに内部死因を載せてブロードキャストしてしまう。

→ `DeathRecord` を `cause`（内部）と `public_cause`（公開）の2層にし、
マスキング表を content 側に持つ。マスキングをコアへ書かない。

**これはプロンプトで隠す方式では絶対に守れない類の漏洩**であり、
マスター仕様 §27 が禁じている「LLMへ一度渡してから忘れろと指示する」の
典型例になりうる。ネットワーク層で落とすこと。

レビュー時の必須チェック項目に追加する:

- 内部死因を含むイベントがクライアントへ送られていないか
- 情報漏洩テスト（`cursed` がクライアント向けイベントに現れない）が存在するか
