# 参照ルールの調査と設計への反映

AIWOLFのルールは、市販の人狼アプリ「人狼ジャッジメント」（そらいろ株式会社）の公式ヘルプを調べたうえで決めました。
この文書は公式仕様の写しではありません。**調査から何を読み取り、AIWOLFの設計をどう決めたか**を説明します。
公式のルールや役職の詳細は、末尾の出典を参照してください。本プロジェクトは非公式で、同社とは関係ありません。

- 調査日: 2026-08-29（関連する設計判断: `Docs/ai/decisions/D003`〜`D012`, `D027`）
- 実際のルールの正本: `content/` のYAMLと `Docs/ai/spec/DESIGN.md`

---

## 1. 役職を5つの独立した軸で表す理由

人狼ゲームの実装では、役職に「村側か人狼側か」という属性を1つだけ持たせることがよくあります。
しかし調査すると、その1つの属性が実際には次の5つの別々の問いを兼ねていることが分かりました。

| AIWOLFの軸 | 答える問い |
|---|---|
| `team` | 誰が勝ったときに、この役職も勝つか |
| `count_as` | 勝敗判定で人数を数えるとき、どちら側の1人として数えるか |
| `attack_result` | 人狼に襲撃されたらどうなるか |
| `inspect_result` | 占い師に何と判定されるか |
| `medium_result` | 霊能者に何と判定されるか |

「陣営が人狼なら占い結果も人狼」のように1つから他を導くと、次の節の役職が表現できません。
そこで5つを別々の属性として持ち、陣営ごとの既定値（`content/teams.yaml` の `default_attributes`）を役職ごとに上書きできるようにしました（D003）。
ゲームコアは「占い師」「狂人」といった役職名を一切参照せず、この属性だけでルールを評価します。

## 2. 単一の陣営属性では表せない反例

| 役職 | 何が食い違うか | 分けた軸 |
|---|---|---|
| 狂人 | 人狼の勝利を目指すが、勝敗判定の人数では村人として数えられる。占っても人狼とは出ない | `team` と `count_as`、`team` と `inspect_result` |
| 大狼（参照アプリの役職、AIWOLFでは未採用） | 占い師には人狼でないと出るが、霊能者には人狼と出る | `inspect_result` と `medium_result` |
| 妖狐 | 村・人狼のどちらにも数えられず、襲撃では死なないが、占われると死ぬ | `count_as` に「数えない」、`attack_result`、占いに反応する受動効果 |
| 人狼 | 仲間の人狼に襲撃されない | `attack_result` |

狂人の例から、勝利条件にも2つの種類が必要だと分かりました。
村の勝利は「人狼という役職が全員いなくなること」で、人狼側の陣営（狂人を含む）の全滅ではありません。
一方で人狼の勝利は「`count_as` で数えた人数の比較」で決まります（D005）。
妖狐は自分だけの条件を持たず、他の陣営が勝つ瞬間に生き残っていればその勝利を奪います。

大狼はAIWOLFの13役職には含めていませんが、占いと霊能を別の軸にした根拠として残しています。
AIWOLFの役職構成を変えずに、YAMLを1つ追加するだけで表現できるはずです。

## 3. 「仲間を知るか」と「秘密会話できるか」を別にした理由

人狼側の協力者には、互いによく似ているのに扱いが違う役職があります。

| AIWOLFの役職 | 陣営 | 仲間を知る（`knows_teammates`） | 人狼チャットに入れる |
|---|---|---|---|
| 狂人 `madman` | 人狼 | 知らない | 入れない |
| 狂信者 `fanatic` | 人狼 | 知る | 入れない |
| 囁く狂人 `whispering_madman` | 人狼 | 知る | 入れる |

3つは陣営も勝利条件も同じで、違いは「誰が仲間か知らされるか」と「どのチャットに書けるか」だけです。
これを陣営や役職名の分岐で書くと、組み合わせの数だけ特別扱いが増えます。
そこで、知識（仲間の通知）とチャットの権限（`chat_channels`）を、陣営とは別の属性にしました。

仲間として通知する相手も役職名では決めていません。陣営に「中心メンバーのタグ」（`teammate_tags`）を宣言し、
`knows_teammates: true` の役職にだけ、サーバがゲーム開始時に該当者を非公開で送ります。
チャットも `content/chat_channels.yaml` で公開・非公開とフェーズを宣言し、配送はサーバが行います。

## 4. 役職固有のルールをYAMLへ分離した理由

参照アプリには、時間・投票・CO・観戦といった全体のルールとは別に、
「初日の占いをどう扱うか」「狩人が同じ人を連続で守れるか」のような**特定の役職だけに関係する設定が数十項目**ありました。
これをゲームコアの条件分岐にすると、役職を1つ追加するたびにPythonを変更することになります。

そこでAIWOLFでは、

- 全体のルールはプリセット（`content/presets/*.yaml` の `rules`）に置く。
- 役職固有の振る舞いは、役職のYAMLに能力（ability）・受動効果（passive）・効果（effect）として宣言する。
- 能力の対象の選び方・制限・効果は、登録済みのIDだけを使える（`selectors.yaml`, `restriction_types.yaml`, `effects.yaml`）。

という2層の構造にしました。ルールはすべて設定で変更できるようにし（D006）、
「役職の追加にPythonの変更が必要なら設計の失敗」を原則にしています。
恋人や狐憑きのように、元の役職を保ったまま勝利条件などを上書きするものは、役職ではなく修飾（Modifier）として別に扱う設計です（D008。標準のプリセットではまだ使っていません）。

調査からは、ほかにも次の設計を決めました。

- **CO（役職の宣言）は自由発言ではなく、システムの操作**として扱う。回数などの制限をサーバが判定できるようにするため（D007）。
- **死因は内部の値と公開する値を分ける**。公開するのは死亡したフェーズから導いた値だけにし、能力の詳細を漏らさない（D012）。

## 5. AIWOLFで実際に採用しているルール

正本は `content/` のYAMLです。ここでは標準の9人プリセット（`content/presets/standard_9.yaml`）の要点をまとめます。

**役職（13種をYAMLで定義）**
村人・占い師・霊能者・狩人・猫又・パン屋（市民陣営）、人狼・賢狼・強欲な人狼・狂人・狂信者・囁く狂人（人狼陣営）、妖狐（妖狐陣営）。
標準の9人の配役は、村人3・人狼2・占い師1・狩人1・狂人1・霊能者1です。

**進行**
- 昼180秒・投票60秒・夜60秒。夜明け直後の15秒は発言できない。時間の延長・短縮はなし。
- 初日の夜の占いは、人狼でない誰か1人の結果がランダムに与えられる（`first_night_seer: random_white`）。
- 突然死・役職欠けは使わない。

**投票**
- 同票なら決選投票を行い、それでも同票なら処刑なし。
- 棄権できる。自分には投票できない。誰が誰に投票したかは公開しない。

**夜の行動**
- 人狼の襲撃先は多数決で、同数ならランダムに決める。
- 夜の行動を選ばなかったとき、サーバが代わりに選ぶのは人狼の襲撃だけ。占い・護衛・霊能は発動しない。
  占いを自動で選ぶと、何もしなかった占い師が偶然妖狐を死なせるおそれがあるため（D027）。
- 狩人は自分を守れず、同じ人を2晩続けて守れない。

**CO**
- 1日3回まで。村人であると宣言するCOは使えない。
- 「2日目以降はCOできない」のような日数の制限は採用せず、昼に発言できるならいつでもCOできる。

**死亡と勝敗**
- 公開する死因は死亡したフェーズから導く（処刑・夜の死亡など）。
- 死者は墓場から公開チャットを見られるが、発言はできない。役職は公開しない。
- 勝敗は市民陣営 → 人狼陣営 → 妖狐陣営の順に評価し、妖狐は他陣営の勝利を上書きする。
