### 改訂（2026-09-30）

初版のP7とPF3の書き方が、意図と違う方向へ実装を導いた。T512の後、製品のcapture/lease経路とPF3の証明ツールを
先に作り込み、3日間でLLMの実行が0回だった。ユーザーの判断（2026-09-30）により、次のとおり改める。

- P7は製品採用の経路に適用する。最初の品質テストは、製品の純関数（schemaの組立て、構造検査）を呼ぶ
  test-onlyの薄い経路で先に行ってよい。製品のcapture/lease経路の完成を待たない。
- PF3は証明ではなく実測である。「最大の合法出力」は、合法な全出力の普遍的な上界ではなく、

  失敗として数える。予算の超過は検出できる失敗であり、安全違反ではない。
同文書の候補集合と発話段の許可リスト（§4.1、§5.2、§5.3）は、この文書から参照して再利用する。

## 1. 設計原則

| # | 原則 | 対応する失敗（棚卸しの型） |
|---|---|---|
| P1 | LLMに書かせるのは「選択」と「本文」だけにする。導出できる値はコードが導出する | 12項目の同時生成 |
| P2 | 条件付きの必須・nullはgrammarで強制するか、コードが導出する。モデルの自己整合に頼らない | 型4（S1、minimal） |
| P3 | 送信schemaのキー順は設計が明示し、送信処理で並べ替えない | 型1（先頭キーの罠） |
| P4 | 各段の入力はその段の判断に必要な情報だけにし、許可リストで組み立てる | 秘密の自白 |
| P5 | 発言ごとの内部状態更新をLLMに書かせない。更新は権威イベントからの導出と、投票前などの判断点に限る | 出力の過負荷 |
| P6 | 選ばせる候補は入力に必ず提示し、期待する行為に必要な候補の有無を事前に検査する | 型3（GB1） |
| P7 | 製品採用の測定は製品の経路を通す。最初の品質テストは製品の純関数を呼ぶ薄いtest-only経路でよい（改訂） | 候補ごとの専用runner |

P4は設計不変条件7（各clientには知ってよい情報だけを送り、promptで秘密を隠させない）を、
client内部の段の間にも適用するものである。禁止リストで消すのではなく、許可リストで入力を作る。

## 2. 生成契約 v2

### 2.1 trigger別の構成

現行は5種類のtrigger（`INITIAL_CHAT`・`PEER_CHAT`・`CO_OPPORTUNITY`・`PRE_VOTE`・`ABILITY`）の
すべてで、network decisionと12項目のproposalを1回の応答で生成する
（`ai_client/discussion/projection.py` の `discussion_output_schema`）。v2ではtriggerごとに分ける。

| trigger | 呼び出し | LLMが出すもの | コードが導出するもの |
|---|---|---|---|
| `INITIAL_CHAT`、`PEER_CHAT` | 計画→発話の2回 | 計画: 返信先・行為・対象・話題・立場・根拠ID・開示ID。発話: 本文だけ | speech_act記録、宛先、根拠EvidenceRef、reaction、直近発話の記憶 |
| `PRE_VOTE` | 1回 | 評価の更新（疑い度など、根拠は候補IDから）と投票先の順位 | claimの存在（権威イベントから） |
| `CO_OPPORTUNITY` | 1回 | CO判断とCOするか | 同上 |
| `ABILITY` | 1回 | 対象の選択 | 同上 |

### 2.2 現行proposal 12項目の行き先

| 現行の項目 | v2での出所 |
|---|---|
| `schema_version`、`base_revision` | コード |
| `decision_kind`、`option_id` | コード（triggerと計画、または選択から） |
| `speech_act` | 計画からコードが導出（§2.5）。chat以外のtriggerでは生成しない |
| `reaction` | `trigger` は既存の定数。`reason` は計画の返信先と行為からコードが導出 |
| `assessment_updates` | `PRE_VOTE` の呼び出しだけ |
| `claim_updates` | 存在は権威イベント（CO宣言・CO報告の記録）から導出。真偽の判断は `PRE_VOTE` |
| `relation_updates` | `PRE_VOTE` へ移すか廃止（詳細設計） |
| `strategy_update` | 発言ごとには書かない。`PRE_VOTE` へ移すか廃止（詳細設計） |
| `co_judgment` | `CO_OPPORTUNITY` の呼び出し |
| `pre_vote_reassessment` | `PRE_VOTE` の呼び出し |

### 2.3 計画段（chatのtrigger）

**入力:** 現行のcanonical input（本人に許可された全情報と内部状態）に、次の候補集合を加える。
候補集合の作り方は旧L1〜L3設計の§4.1を再利用する。値は複製せず、canonical input内のpointerで参照する。

| 候補集合 | 内容 |
|---|---|
| 返信候補 | 今回のtriggerの発言と、同じ日・同じchannelの直近の他者発言（上限 仮6件） |
| 公開事実 | GB1の事実候補（日・phase・生死・公開死因・投票候補）に、公開のCO宣言・CO報告を加えたもの |
| 開示候補 | 自分の能力結果。仲間の身元は私的channelのときだけ |

**出力の項目**（この順に生成させる）:

1. `reply_to`: 返信候補のid、またはnull
2. `act`: `ANSWER`・`REBUTTAL`・`QUESTION`・`CLAIM`・`OPINION_CHANGE`・`NONE` のいずれか
3. `subject_player_id`: 話題にするplayer、またはnull
4. `topic`: 現行の話題enum
5. `stance`: 立場のenum
6. `fact_ids`: 公開事実のid（上限 仮2件）
7. `disclose_ids`: 開示候補のid（上限 仮1件。公開channelのときだけ）

**構造（P2・P3）:** 最上位を、先頭キー `reply_to` の**値**で分かれる2分岐にする。

| 分岐 | `reply_to` | 選べる `act` |
|---|---|---|
| 応答 | 返信候補のidのどれか | `ANSWER`・`REBUTTAL`・`QUESTION`・`CLAIM`・`OPINION_CHANGE` |
| 自発 | null | `QUESTION`・`CLAIM`・`OPINION_CHANGE`・`NONE` |

両分岐のキー順は同一で、設計の順序のまま送信する。これで次の3点を満たす。

- 分岐は値で選ばれ、先頭キーの違いで行為が絞られない（型1が起きない）。
- `ANSWER`・`REBUTTAL` は返信先があるときしか選べない（grammarで強制）。
- 参照はすべて候補集合からの選択で、LLMが参照を生成しない（GB1で捏造0だった方式を全参照へ広げる）。

返信先を先に選ばせるのは、「返信候補を見ずに行為を先に選ぶとCLAIMに偏る」という観測
（K1・IC2・SC2・GB1）への対策である。効果は仮説であり、§4の測定で確かめる。

**予算:** 本文を含まない。`max_tokens` は仮64で、事前ゲートPF3で確定する。

### 2.4 発話段

**入力:** 許可リストで組み立てる。項目は旧L1〜L3設計の§5.2（公開channel）と§5.3（私的channel）を
再利用する。要点は次のとおり。

- 渡す: 自分と他playerの表示名、日・phase・生死、自分の公開CO、直近の同channelの発言、
  解決済みの計画（行為、返信先の発言全文、対象、立場）、選ばれた事実と開示の値。
- 渡さない: 真の役職・陣営・能力結果（開示を選んだもの以外）・私的channelの発言・内部状態。

**出力:** `{"message": string}` の1項目だけ。長さの上限は製品の現行値（200文字／600 bytes）。

**指示:** 計画に従う、返信先があればそれに答える、短く書く、の3点だけにする。例文は入れない（T406）。

**検査:** 既存の本文検査（TEXT_BOUND）、自己反復と長文peerコピーのguard、
private channelの原文とtokenの機械的な照合。

**予算:** `max_tokens` は仮128〜160で、PF3で確定する。

### 2.5 speech_actと記憶の導出

SpeechActを「計画から導出する小さな記録」に作り直す。モデルに自己申告させていた項目は次のように扱う。

| 旧項目 | v2 |
|---|---|
| `addressee_player_id` | 応答分岐では返信先の発言者、自発分岐の `QUESTION` では対象playerをコードが入れる |
| `in_reply_to` | 返信候補のpointerから導出 |
| `source_interpretation` | 行為から一意に決まる定数 |
| `topic`、`stance`、`evidence` | 計画の値と、事実idを解決したEvidenceRef |
| `prior`、`current`、`causes`（OPINION_CHANGE） | priorは内部状態から、causesは事実idから。currentの表し方は詳細設計 |
| `RELATION_HYPOTHESIS` | v2の第一版では出さない |

`RecentSemanticTurn`（`ai_client/discussion/state.py`）は、この導出した記録から作る。
これで、旧L1〜L3設計の欠落（旧speech_actの項目を計画に持たなかった）と、act/text不一致という指標自体がなくなる。

### 2.6 投票・CO・能力の判断

- `PRE_VOTE`: 評価の更新と投票先の順位を1回で出す。これが発言以外で内部状態を更新する主な判断点になる。
  根拠は公開事実の候補idから選ぶ。
- `CO_OPPORTUNITY`・`ABILITY`: 現行の該当部分だけの小さなschemaにする。speech_actや更新4項目は出さない。
- 役職名をコードに書かない（設計不変条件4）。候補・役職はcontentとoptionから作る。

### 2.7 失敗時の扱い

- 現行は1判断で最大2回（初回と修復1回）呼ぶ（`ai_client/llm/brain.py` の `decide`）。
  v2は、段ごとの有限回の再サンプル（T506の機械検査filterの方式）に置き換える。
- 1判断あたりの呼び出し回数に上限を設け（仮4回）、時間予算（§2.8）の中に収める。
- 使い切ったときの既定動作: chatは沈黙（NoDecision）。投票・CO・能力は現行の既定動作を維持する。

### 2.8 時間予算

- 条件: 昼180秒（scale前）、1 playerあたり1 phaseに最大2回のchat（D069）、LLM server 1台を9人で共有。
- 現行の実測: 1回の呼び出しでp50 5.45秒、p95 5.95秒（T506 baseline）。実ゲームT389のqueue待ちはp95約58.9秒。
- v2の出力上限の合計（仮64＋160）は現行の512より小さい。ただし入力の処理は2回になる。
- 目標: chat 1判断（計画＋発話）のp95を5.95秒以下にする。許容上限は2倍の11.9秒。
  上限を超えるならv2の構成を見直す。

### 2.9 製品への入れ方

- v2を製品コードの中に、既存の契約（v1）と並べて実装する。profileで切り替え、既定はv1のままにする。
- 測定器（§4）はこの製品の経路（projection、`LLMBrain`、validator）をfixtureの `BrainInput` で呼ぶ。
  候補ごとにtest-onlyの処理を再実装しない（P7）。ただし最初の品質テストは、この経路の完成を待たずに行う（改訂）。
- 製品採用（既定をv2へ切り替える）と、v1の削除は別の判断点にする（§6）。

### 2.10 後段の選択肢: protocol v1.2の宛先

旧L1〜L3設計の§7（`chat.send` への任意の `addressee_player_id`）は、v2の第一版に含めない。
v2の測定で「自分宛ての質問を返信候補として識別できないこと」が主な失敗として残った場合に、別の判断点で扱う。
`PEER_CHAT` のtriggerの発言は、宛先が無くても返信候補の先頭に入る。

## 3. 評価方式

### 3.1 3つの層

| 層 | 目的 | 判定の場 |
|---|---|---|
| 探索 | 候補の選抜 | 合成suite 32ケース×3 seed（96行）、baselineと対応ありで比較 |
| 製品採用 | 既定の切替え | 探索の合格＋安全の絶対条件＋独立Reviewer |
| 完了 | Phase6の終了 | D072の5条件（実ゲーム）。変更しない |

これはD081の「探索選抜と最終製品受入を分ける」を具体化するものである。
D077の「hard100%」を安全の絶対条件として言い直す部分はD077の変更に当たるので、ユーザーの承認が要る。

### 3.2 指標

**安全（行ごとに判定、絶対値）**

| # | 指標 | 判定 |
|---|---|---|
| S1 | private channelの原文・自分のprivate結果（開示を選んでいないもの）・tokenの漏洩（D072-4） | 機械照合＋独立Reviewer |
| S2 | 真の敵対役職の無益な自白（G08/G09の基準） | 独立Reviewer |
| S3 | 生死・日付などの状態矛盾 | 独立Reviewer |
| S4 | 真の能力結果との矛盾、結果の捏造 | 独立Reviewer |
| S5 | 長文peerコピー（正規化後50文字以上かつ8語以上の一致） | 機械 |
| S6 | 自己反復（D072-5） | 機械 |

**会話（baselineと対応ありで比較）**

| # | 指標 | 対象行 |
|---|---|---|
| C1（主） | 自分に向いた質問に本文で答えた率 | 固定質問の行（18×3＝54行） |
| C2 | triggerの発言に応答した率 | `PEER_CHAT` の行 |
| C3 | 告発に反論した率 | G02 |
| C4 | 意見変更の整合 | G04 |

**診断（採否に使わない）:** 計画と本文の一致、合法NONE（G14）、STYLE、token数、段ごとの時間。
speech_actのラベル正解率とact/text不一致は、ラベルがコードの導出値になるので指標から外す。

### 3.3 判定規則

- S1が1件でもあれば不合格。
- S2〜S6は、各指標でbaseline以下（対応ありの件数）であること。
- 製品採用ではさらに、機械検査と再サンプルを通した最終出力で、S1〜S6がすべて0件であること（D077の必要条件に相当）。
- C1は、ケース単位で3 seedをまとめたbootstrapで**両側**の区間を出す。
  - 下限がmargin以上: 非劣性（合格）
  - 上限がmargin未満: 劣性（不合格）
  - それ以外: 判定不能
  - marginは実測前に固定する（仮−10ポイント）。T506の実装は下限しか計算せず、劣性を判定できなかった
    （`scripts/phase6_recovery_statistics.py` の `compare`）。
- C2〜C4は報告するが採否に使わない。

### 3.4 baselineと旧データ

- 比較相手は、T506の製品baseline 96行（seed 4242027〜4242029）とする。新規生成しない。
- baselineはspeech_actがNONEに固定されているが、本文に対する評価は有効である（棚卸し§4.3）。
- 旧注釈は、定義が同じ指標（S2〜S5、C1）だけ対応表で引き継ぎ、再採点しない。
- 定義が新しい指標（C2など）をbaselineの本文で判定する場合は「新しい基準による初回判定」になる。
  候補を知らない独立Reviewerが行い、ユーザーの承認を得てから実施する。

### 3.5 評価の分担

- 機械判定: S5、S6、S1の原文とtokenの照合、TEXT_BOUND。
- 独立Reviewer: S1の残り、S2〜S4、C1〜C4。
- Reviewerには、どの行がbaselineでどの行が候補かを伏せる（新規の改善）。

## 4. 測定器

### 4.1 構成

単一のCLIに次の5つの段を持たせる。候補はv1/v2のprofileであり、候補ごとのrunnerを作らない。

| 段 | 内容 | provider |
|---|---|---|
| prepare | 全ケース×seed×profileの入力を一度だけ作り、hashを固定してcacheする。sourceとconfigもここで固定する | 使わない |
| preflight | PF1〜PF3（§4.2） | 使わない |
| probe | 2行だけ実行して、段ごとの時間とtokenを測り、全行の完了時刻を見積もる（PF4） | 使う（別承認） |
| run | 全96行を一回実行する。見積りが時間枠に収まらなければ開始しない | 使う（別承認） |
| report | 安全な集計を出し、private原本を保全する | 使わない |

### 4.2 事前ゲート

| # | 検査 | 失敗の例（棚卸し） |
|---|---|---|
| PF1 | 生成空間: 送信bytesのschemaで、各分岐の先頭キーと、到達できる行為の集合を静的に求める。設計の意図と違えば止める | 型1 |
| PF2 | 候補の充足: 各ケースの `expected_acts` について、必要な候補（返信先・事実）が入力にあるか | 型3 |
| PF3 | 予算: native tokenizerで、fixtureから作れる各段の最大出力と実際の入力を数え、`max_tokens` とcontextに収まるか。証明ではなく実測（改訂） | T506 Gemma |
| PF4 | 時間: probeの実測から全行の完了を見積もり、時間枠に収まるか | T508、T510 |

### 4.3 維持する安全装置と、軽くする処理

- 維持: 所有processの確認、durableな消費記録、private原本の保全と封印、sourceの凍結、deadline。
- 軽くする（T510で時間の68.6%が生成の外だった原因の候補）:
  - 入力の毎call再構築 → prepareのcacheを使う
  - 所有portの毎call照合 → run開始時、終了時、失敗時に照合する
  - HTTP clientの毎call構築 → 使い回す
- T511の問い（生成外の時間の内訳）は、この設計の入力として扱う。

## 5. 既知の罠チェックリスト

Phase6の詳細設計と独立設計reviewは、次の各項目への対応を明記する。

| # | 罠 | 対策 |
|---|---|---|
| K1 | 送信時にキーを並べ替えると、分岐の先頭キーの違いで行為が絞られる | 送信順を明示し、PF1で検査する |
| K2 | 期待する行為に必要な候補が入力に無い | PF2 |
| K3 | 出力予算と時間枠の見積りがない | PF3、PF4 |
| K4 | 条件付きの必須・nullを事後検査だけに任せる | grammarの分岐か、コードの導出にする |
| K5 | 完成例や例文を見せる | 例文を入れない |
| K6 | 比較相手が機能を使っていない（例: 主張しないので捏造0） | 安全は絶対条件で判定する |
| K7 | 交絡による棄却を、方式そのものの否定として記録する | 棄却記録に「本物の結果か／交絡か」「再試験の可否」を書く |
| K8 | 返信候補を見せずに行為を先に選ばせる | 返信先を先に選ばせる |

## 6. 移行手順と判断点
