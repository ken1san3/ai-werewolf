## Q18 [Phase 1 前に必須] 乱数の決定性とシード管理

**最優先。後付けがほぼ不可能。**

現時点で乱数を使う箇所が既に5つある。

```
役職配布
役職欠け（D006）
初日ランダム白（D006）
投票同数のランダム処刑（D006）
猫又の道連れ対象抽選（D011）
```

Phase 5 以降では LLM のサンプリングも加わる。

乱数源を各所で `random.random()` するとリプレイが再現しない。
マスター仕様 §24 は `random seed` をログ項目に挙げ、
§25 はイベントログからのリプレイを求めているが、
**乱数の管理方針がどこにも書かれていない。**

Reviewer 推奨:

- ゲームごとに1つのシードを持ち、**すべての乱数を単一の RNG から引く**
- モジュールレベルの `random` を直接使うことを禁止し、
  `game.rng` を経由させる（レビューの指摘対象にする）
- 用途ごとに派生 RNG を作る（`rng.derive("vote_tie")` 等）。
  こうすると新しいランダム要素を足しても既存の乱数列がずれない
- シードをゲームログの先頭に記録し、同じシードで同じ試合が再現できる
  ことをテストで保証する
- LLM の非決定性はゲームコアの外側にあるため、
  「Dummy Brain のみなら完全再現」を目標にする

## Q19 [Phase 1.3 前] フェーズ状態機械の確定

マスター仕様 §6 のイベント列にはフェーズ関連が並んでいるが、
**状態遷移図としては定義されていない。**

未確定:

- ゲームは初日の朝から始まるか、昼から始まるか
- 初夜（Night 0）が存在するか（初日占い「あり」の場合の占いはどこで行われるか）
- 決選投票（D006）はどのフェーズとして表現するか
- 夜明けの結果発表を独立フェーズにするか、昼の先頭に含めるか
- 15秒ルール（D006 の `silence_after_dawn_seconds`）はどのフェーズの属性か

Reviewer 推奨:

```
Setup
 → [Night0]（初日占い設定が none 以外のときのみ）
 → Dawn（結果発表・15秒ルール）
 → Day（議論）
 → Vote
 → [Runoff]（同数かつ決選投票ありのときのみ）
 → Execution
 → Night（夜行動）
 → Dawn ...
 → GameEnd
```

- 条件つきフェーズ（Night0 / Runoff）が存在する形にしておくと、
  役職追加でフェーズが増えても構造が壊れない
- GAME_END_CHECK は Execution 後と Dawn 前の2箇所で走る（D005 と整合）

## Q20 [Phase 1.5 前] 夜の解決順と能力の相互作用

マスター仕様 §11 は解決順の**例**を挙げているだけで、
本プロジェクトの13役職（D009）に対する具体的な順序が未確定。

Reviewer 提案:

| priority | 処理 | 備考 |
|---|---|---|
| 30 | Protect（狩人の護衛） | |
| 40 | Inspect（占い） | 呪殺の判定もここ。死亡フラグを立てるだけ |
| 50 | Attack（襲撃） | 妖狐の耐性・護衛をここで評価 |
| 70 | DeathResolve | ここで死亡を確定させる |
| 75 | InspectDeadRole（賢狼） | D010。死亡確定後 |
| 78 | Retaliation（猫又の道連れ） | D011。賢狼への通知より後 |
| 80 | FollowDeath（後追い） | Phase 8 |
| 90 | GAME_END_CHECK | D005。全死亡解決後に1回 |

これに伴い確認したい点:

1. **狩人の護衛は呪殺を防ぐか** → 推奨: **防がない**。
   参照実装は「人狼襲撃から護衛」と明記している
2. **占い師が同じ夜に襲撃されても占いは成立するか** → 推奨: **成立する**。
   Inspect(40) が Attack(50) より先。
   つまり**占い師が噛まれた夜でも呪殺は発生する**。
   これは人狼側のセオリーに直結するため、明示的に決めておくこと
3. 同一プレイヤーに複数の死亡要因が来た場合、内部死因はどれになるか
   → 推奨: **priority が先のもの**（呪殺と襲撃が重なれば `cursed`）。
   公開死因は D012 によりどちらも `died_in_night` なので外部差は無い
4. 強欲な人狼の2人襲撃で、片方だけ護衛された場合の扱い
   → 推奨: 対象ごとに独立に評価する

## Q21 [Phase 1.6 前] 引き分け・全滅の扱い

`decisions/D005` に**引き分けの規定が無い。**

これは理論上の話ではなく、実際に起こる。

```
残り2人（人狼1・猫又1）
→ 猫又を処刑（lynched）
→ 道連れで生存者から1名 = 人狼が死亡（retaliation）
→ 全員死亡
```

D005 は「全死亡処理の解決後に1回判定」なので、
この時点で市民陣営の勝利条件（全人狼死亡）も
人狼陣営の勝利条件（市民数 ≤ 人狼数、0 ≤ 0）も同時に成立しうる。

未確定:

- 全員死亡したときの勝敗
- 複数陣営の勝利条件が同時成立したときの優先順位
- 妖狐の便乗勝利（D005）と同時成立の関係

Reviewer 推奨:

- 勝敗結果の型に **`draw`（引き分け）を最初から含める**。
  後から足すと勝敗判定・ログ・リプレイ・戦績すべてに波及する
- 同時成立の優先順位を content 側の設定として明示する
  （既定: 市民 > 人狼 > 第三陣営 の順に評価し、最後に便乗型を適用）
- 生存者0人は `draw` とする

## Q22 [Phase 1.5 前] 能力の結果を誰に通知するか

各能力の「成功・失敗」を使用者へ返すかが未定義。
これは `decisions/D012` と同じく**情報設計の問題**であり、
実装後に変えると漏洩の修正になる。

| 状況 | 使用者は知るか | 推奨 |
|---|---|---|
| 狩人の護衛が襲撃を防いだ（GJ） | ? | **知る**（参照実装はGJ表示あり） |
| 狩人の護衛先が襲撃されなかった | ? | **知らない**（GJと区別する） |
| 占い師が妖狐を占って呪殺した | ? | **判定結果は「人狼でない」のみ**。呪殺したことは知らない |
| 人狼の襲撃が防がれた | ? | 朝の結果から分かるため、専用通知は**出さない** |
| 賢狼の情報 | D010 で決定済み | 襲撃成功時のみ |

特に3つめが重要。**占い師が「呪殺した」と即座に分かると、
妖狐の死が村側へ確定情報として流れる。**
D012 で公開死因をマスクした意味が無くなる。

参照実装でも、占い師は「人狼でない」判定を得るだけで、
呪殺したかどうかは翌朝の死亡者から推測するしかない。

## Q23 [Phase 1 前] available_actions をゲームコアが返せるようにするか

マスター仕様 §33 は「サーバはAIへ現在可能な操作を具体的に返す」と定めている。
これは Phase 2 の話に見えるが、
**ゲームコア側に「あるプレイヤーが今できる行動の一覧」を返す API が無いと、
Phase 2 でネットワーク層に判定ロジックを再実装することになる**
（＝ルールが2箇所に分散し、D001 のサーバ権威が崩れる）。

Reviewer 推奨: Phase 1 の時点で

```python
game.get_available_actions(player_id) -> list[ActionSpec]
```

を用意し、Dummy Client のテストでもこれを経由させる。
ネットワーク層は**この結果をそのまま整形して送るだけ**にする。
