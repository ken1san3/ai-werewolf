## Q11 [Phase 2] チャットチャネルの初期スコープ

参照実装には「墓場の発言」「観戦者の発言」の設定がある。
マスター仕様 §22 のチャネル案は `public / wolf / lover / spectator / system / private`。

Phase 2 でどこまで実装するか。

Reviewer 推奨: `public` / `wolf` / `system` / `private:<player_id>` の4つ。
`graveyard`（墓場）と `spectator` はチャネル定義だけ用意し、送信は Phase 7 で。

## Q31 [Phase 1.8 / 2] 突然死の発動条件

`sudden_death` は死因の語彙に存在し、霊能者の判定対象にも
`targets: [lynched, sudden_death]` として入っている。
しかし**何が引き金で発生するのかがどこにも書かれていない。**
現状、突然死は起こりえないのに霊能者はそれを占える宣言を持っている。

参照実装は「時間内に発言しなかった」「投票しなかった」場合の突然死設定を持つ。
AI主体のプラットフォームでは、これは頻繁に起きる。

候補: 昼に一度も発言しない / 投票しない / 接続断が一定時間続く / 発生させない

Reviewer 推奨: `rules.sudden_death` を設け、既定は無効。
引き金は「投票しなかった」ではなく（Q5 の未選択フォールバックと衝突する）、
**「昼に一度も発言しなかった」** に限る。Phase 1 では発生させず、
Phase 2 で発言の有無を数えられるようになってから有効化する。

## Q32 [Phase 2 前] 切断・タイムアウト時のゲームの扱い

ROADMAP 2.2 は「切断」を含むとしているが、切断されたプレイヤーのゲームを
どう扱うかが決まっていない。

候補: ゲームを中断 / そのまま進行 / 突然死させる / サーバがAI代行する

Reviewer 推奨: **そのまま進行させる。** サーバ権威（D001）なので、
接続の有無は進行に影響しない。未選択は Q5 の `no_selection` が吸収する。
切断を突然死に直結させない。AI主体の構成では接続断が日常的に起きるため、
それが死因になると対戦が成立しない。

## Q33 [Phase 2 前] 再接続時の本人確認

`game.state_sync` は private 情報（自分の役職・能力結果）を含む。
再接続クライアントが「自分は player3 だ」と自己申告できると、
**他人の役職と占い結果がそのまま漏れる。**
現在この検証方法がどこにも書かれていない。

Reviewer 推奨: Join 時にサーバが接続トークンを発行し、再接続はトークンで照合する。
`player_id` の自己申告を信用しない（D001）。
これは技術的な決定なので、指示がなければ Reviewer が DESIGN §9 に書く。

## Q34 [Phase 2 前] 時間を進める主体と時刻源

ゲームコアは `now` を受け取る受動側で、自分では時間を進めない
（`advance_if_due(now)`）。誰が何秒間隔でこれを呼ぶか、
時刻源は何か、サーバが遅延したときに締切が伸びるかが未定義。

Reviewer 推奨: サーバの単調時計を唯一の時刻源とし、1秒間隔の tick で
全ゲームの `advance_if_due` を呼ぶ。締切は絶対時刻で保持しているため、
tick が遅れても締切は伸びない。
これは技術的な決定なので、指示がなければ Reviewer が DESIGN §9 に書く。

## Q35 [Phase 2 / 7] 死亡プレイヤーの情報範囲

死亡後に何が見えるかが決まっていない。
`graveyard` チャネルは Phase 7 とされているが、
「死亡者が public チャットを見続けられるか」「役職が公開されるか」は
Phase 2 の送信分離を作る時点で決めておく必要がある。

参照実装は墓場の発言可否を設定で持つ。

Reviewer 推奨: `rules.graveyard` として持ち、既定は
「public の閲覧は継続、発言は不可、役職は公開しない」。
死亡者に生存者以上の情報を渡さないことを既定にすれば、
観戦・墓場を後から足しても情報漏洩の検証項目が変わらない。
