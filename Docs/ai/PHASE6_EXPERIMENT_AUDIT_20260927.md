# Phase 6 品質実験の棚卸し：再利用できるものと書き直すべきもの

Status: FINDINGS（外部レビュー。未承認。製品変更0、provider操作0、新規生成0）
作成: 2026-09-27
作成者: Claude Code

## 結論

- **設計・計画の不備で失敗扱いになったのはT510だけではない。** 合成suite期（T406〜T510、2026-09-18〜27）の
  試行19件のうち**13件**は、設計・計画の不備によって候補の良し悪しを測れていない。
  候補の性能を示した本物の結果は6件。
- 不備は4つの型の繰り返しである。特に「先頭キーの罠」は、チームが2026-09-19に特定した**後も5回再発**した。
- その下に構造問題が2つある。
  1. 1回の呼び出しで、発言と12項目の内部状態を同時に生成させる製品契約。
  2. Phase6の完了条件（D072）が要求していないラベル整合を、採否の軸にした評価。
- 書き直すべきなのは**生成契約・評価基準・実験基盤（知識の引継ぎを含む）**の3つ。
  安全境界、評価用の合成suite、部品関数、本物の発見、保存済み本文の評価は再利用できる。

## 調査範囲と方法

- 読んだもの: decisions D069〜D084、Phase6の失敗記録、`history/` の完了記録、各結果文書、
  ROADMAPのPhase6完了条件、製品設計の§2/§7、各実験toolの送信処理。

  コード確認を組み合わせた。
- 旧結果の再生成・再採点、provider操作、製品変更はしていない。private原文は読んでいない。

## 2. 繰り返した欠陥の型

### 型1: 先頭キーの罠（8件）

製品と実験toolは、送信するschemaのキーを再帰的にアルファベット順へ並べ替える
（`ai_client/llm/backend.py:326`、`scripts/phase6_context_probe.py:22`）。
speech_actの7分岐のうち、先頭キーが `kind` になる分岐はNONEだけである。
モデルが `{"kind"` から書き始めると、文法上NONEしか選べない。

- 2026-09-19の静的解析で特定済みだった（[静的解析](PHASE6_STRUCTURED_OUTPUT_STATIC_20260919.md)）。
- それでも、その後の5件は既定の送信処理のままで、全件NONEになった。

| 試行 | 罠が残った箇所 |
|---|---|
| I1 | 外枠の順序だけ戻し、分岐の中は並べ替えたまま（`scripts/phase6_intent_first_probe.py:211`） |
| P2 | 計画段が旧speech_actを持ち、並べ替えて送信（`scripts/phase6_two_call_probe.py:100`） |
| minimal | 製品の `_speech_schema` を並べ替えて送信（`scripts/phase6_minimal_output_probe.py:245`） |
| derived | minimalの送信処理を再利用（`scripts/phase6_derived_grounding_runner.py`） |
| T510 | 計画段Tが旧speech_actを持ち、並べ替えて送信（`scripts/phase6_local_staged_runner.py:83`） |

再発した経緯:

- K1の結論が「kind-firstは不採用、oneOfの微調整は打ち切り」とまとめられた。
  「罠がある」という知識ではなく「kind-firstは駄目」という結論が残り、後続の設計は罠のある既定順を使った。
- I1の失敗記録は「限定実装欠陥は未確認」としている。
  独立レビューは権限・秘密・証拠の対応付けを厳密に見たが、「この候補はNONE以外を出せるか」は見ていない。
- T406の「NONE固定をgrammar制約のせいにできない」という誤った結論は、2026-09-19まで残った。
  完成例を見せた候補がNONEを回避できたのは、例のキー順をなぞったためと考えられる。
- T510の元になった私の段階設計（[§4.2](design/PHASE6_LOCAL_STAGED_DISCUSSION_DESIGN.md)）にも欠落があった。
  平坦な計画schemaに、旧speech_actが要求する `topic`・`evidence`・`prior`/`current`/`causes` が無かった。
  実装側が旧構造をTに出させた判断には、主観stateを補完しないという正当な理由がある。

### 型2: 事前の時間・予算見積りがない（5件）

T400、T389、T506 Gemma、T508、T510。どれも1〜2行を先に実測すれば防げた。
T510では実時間の68.6%が生成の外で消費された（全32入力の毎call再構築、所有port照合、HTTP client構築を観測）。

### 型3: 入力に必要な情報がない

GB1の事実候補は、日付・生死・投票候補・能力結果だけである。発言記録とCOを含まない
（`scripts/phase6_grounding_basis_probe.py:47`）。
このためANSWERの根拠を選べず、T506でのANSWER選択は96件中1件だった。
T506はこの欠陥を引き継ぎ、質問回答の基準で不合格になった。
D082も、未使用の「本人宛て未回答」の候補集合を別設計の範囲として残している。

### 型4: grammarが強制しない制約をモデルに守らせる

- S1: ラベルごとの必須・nullの条件をschemaで表さず、事後検査だけにした。
  非該当fieldの非null 25件、必須null 24件で、構造不適合は30/32件。
- minimal: 同じ根拠を2箇所に書かせ、機械不受理28件のうち24件が不一致だった。

## 3. 構造的に書き直すべき場所

### 3.1 生成契約（最優先）

現状:

- 製品設計は、1回の応答でnetwork decisionと12項目のproposalを同時に生成し、2回目の呼び出しをしないと定める
  （[設計§2](design/PHASE6_DISCUSSION_QUALITY_DESIGN.md)）。
- 19件の試行は、すべてこの契約の中で512 tokenに収める工夫だった。
- speech_actはサーバに届かない。製品内では、検証と「自分の直近発話の記憶」（`RecentSemanticTurn`、
  `ai_client/discussion/state.py:994`）に使われるだけである。
- 実ゲームT389では、この大きな出力の構造不正と修復失敗が多発した。

書き直しの方針:

1. **計画:** 平坦な構造にし、選択肢と候補IDを選ぶだけにする。kindを先頭に置き、返信先の候補を見せる。
2. **発話:** 本文だけを書かせる。入力は許可済みの公開情報に限る。
3. **内部状態の更新:** 発言ごとにLLMへ書かせない。コードで導出するか、投票前などにまとめて別の呼び出しで行う。
4. **SpeechAct:** 計画から導出する小さな記録に作り直す。
   旧来の `topic`・`source_interpretation`・`prior`/`current`/`causes` をモデルに自己申告させない。
   これで型1の前提と、§2で述べた私の設計の欠落、act/text不一致という指標自体が消える。

影響範囲:

- `ai_client/discussion/` の `model.py`・`state.py`・`transaction.py`・`projection.py`（計約4,900行）は
  proposalを中心に組まれている。全部が作り直しになるわけではない。
- World State、権限と可視性、capture、Logical Game Clock、admission/brokerは維持できる。
- 時間予算の制約がある。1 phaseあたり9人×最大2発言（D069）で、LLMは1台を共有する。
  T389のqueue待ちはp95で約58.9秒だった。新契約は、現行の1回512 tokenより軽いことを事前に示す必要がある。

### 3.2 評価基準

- **比較相手のbaselineが退化している。**
  - baselineのspeech_actは100% NONEで、発言ラベルに付く根拠を一度も出していない。
    その「捏造0」は「主張しないので捏造もない」状態である。
  - K1・IC2・GB1など、NONEを脱した候補は常にこの0と比べられた。
  - act/text不一致23も、NONEに会話的な本文が付くことで生じる値である。
- **全指標が悪化しないことを求める基準は、小標本では偶然でも通りにくい。**
  D081でact/text不一致は診断用に下げたが、主・副指標の非劣性の要求は残っている。
- **完了条件はラベルを要求していない。** D072の完了条件（[ROADMAP](ROADMAP.md)）は次の5つだけである。
  1. 9 AIで1ゲーム完走し、所有process残存0。
  2. 他人の発言を受けた応答発言の受理が1件以上。
  3. 質問→回答、主張→反論、意見変更のいずれかを、独立Reviewerが原文で1件以上確認。
  4. private channel本文・自分のprivate結果・tokenの漏洩0。
  5. 同一文の反復が基準内。
- D077以降の合成suiteは、ラベルとact/textの整合を軸にしたため、完了条件から離れた。

書き直しの方針:

- 漏洩・秘密の自白・状態や能力の矛盾・長文コピーは、絶対値の上限として判定する。
- 質問への回答率や応答率などの会話指標は、同じケース・同じseed同士で比べる。
- 完了条件に直結する指標を主指標にし、ラベルは導出値として検査対象から外す。
- D077とD081はユーザー指示で決まったので、変えるにはユーザーの判断が必要。

### 3.3 実験基盤と知識の引継ぎ

現状:

- 候補ごとに設計書（15〜28KB）、独立審査、専用runner、実行条件の凍結を作っている。
- Phase6の試験用toolは40本・11,213行、テストは55本・25,587行ある。

書き直しの方針:

- 候補を差し込み式の純関数（入力構築・schema・組立）にし、単一の測定器へ統合する。入力はcacheする。
- 次の事前ゲートを必須にする。
  1. 生成できる出力の静的検査: 全ラベルに到達できるか、各分岐の先頭キーは何か。
  2. 1〜2行での時間とtokenの実測と、全行の完走見積り。
  3. 期待する発話行為ごとに、必要な候補（返信先・根拠）が入力に揃っているか。
- 既知の罠を短いチェックリストにし、設計審査の必須項目にする。
- 棄却記録に「本物の結果か、交絡か」と「再試験の可否」の欄を設ける。

## 4. 再利用できるもの

### 4.1 そのまま使える資産

- 製品の安全境界: World State、権限と可視性、capture/transaction、validator、Logical Game Clock、admission/broker。
- 合成suiteの32ケース（[G01〜G16](PHASE6_SYNTHETIC_SUITE.md)）、T506の3 seed拡張、3層の採点基準、独立意味評価の手順。
- 部品:

| 部品 | 出所 | 使い方 |
|---|---|---|
| kind-first helper | K1（T437） | 旧schemaを使う間の罠回避 |
| 事実候補集合 | GB1 | 発言記録とCOを加えて計画段の候補にする |
| CO整合helper | T487 | そのまま |
| 参照の閉集合化 | GC2 | 計画段の参照制約 |
| 空配列のconverter互換修正 | C5 | そのまま |
| K回再サンプル＋機械検査filter | T506 | HARD fail 27→5/96の実績。安全網として維持 |
| 入力allowlistと発話段 | T510 | 新契約の発話段 |
| 無損失の組立 | P2 | 旧形式との互換が必要な間 |
| native tokenizer計数 | T448 | 事前ゲートの予算見積り |

### 4.2 設計の前提にすべき本物の発見

1. 完成例を見せると本文をコピーする（T406: 26/28件）。
2. 返信候補を見せずにラベルを先に選ばせると、CLAIMに偏りANSWERをほぼ選ばない
   （K1 CLAIM26/32、IC2 27/32、SC2 25/32、T506 GB1 CLAIM62・ANSWER1/96）。
3. 参照IDが存在しても、主張を支えているとは限らない（K1の捏造8件）。
   候補集合から選ばせると捏造は0になった（GB1、T506で4→0）。
4. grammarが強制しない条件はモデルが守れない（S1）。
5. 出力を最小にすると、他者発言のコピーが急増する（minimal 20件、derived 22件）。
6. 秘密を発話段に渡さないと、秘密の自白が消えた可能性がある
   （T510の観測23行で0件、秘密保持4ケースを含む。弱い証拠）。

### 4.3 保存データ

- 罠で交絡した実験でも、本文の評価（秘密開示・コピー・本文での回答）は有効であり、再生成せずに再利用できる。
  無効なのは、speech_actラベルとact/text不一致に関する指標だけである。
- モデル比較（T424-428）も同じで、本文の比較は有効、ラベルの比較は無効。

### 4.4 交絡で棄却された候補の扱い

| 候補 | 扱い |
|---|---|
| I1 intent-first / P2 2段 | 新しい生成契約の骨格そのもの。個別の再試験は不要 |
| minimal / derived（根拠の重複除去） | 計画段で根拠を一度だけ選ぶ形で新契約に吸収 |
| C1 / C2 | 微調整なので再試験しない |
| T510 L1（入力の分離） | 新契約の発話段として再測定する |
| Gemma | 新契約の予算で互換性を再測定する |

## 5. 進め方の案と判断事項

進め方の案:

1. 評価基準と事前ゲートを作り直す。安く、以降の浪費を止められる。
2. 新しい生成契約を設計する。D051に従い、Architectと独立審査を通す。
3. 2と並行して測定器を統合する。
4. 新契約と現製品を96行で比較し、D072に沿って実ゲームを1回行う。

ユーザーの判断が必要な点:

- **評価基準:** D077/D081の採否基準を、D072の完了条件寄りに作り直すか。
- **製品契約:** 「2回目の呼び出しなし」を撤回し、発言と内部状態の更新を分けるか。
- **hold:** 現holdは新しい測定と製品変更を禁じている。この方向へ進むなら、どこまで解除するか。

## 限界

- 各試行の全handoffは読んでいない。決定・失敗・結果の記録とコードで判定した。
- 罠の判定は、保存結果のNONE件数と送信処理のコードに基づく。各試行で罠が唯一の原因だったとは断定しない。
  罠を外した場合も、ラベル先決めの偏り（§4.2の2）は残る可能性がある。
- S1とGB1を⚠に分類したのは、私の判断である。
- 試行の数え方は、行の分け方で変わる（例: IC2/GC2/SC2を1件とするか）。
