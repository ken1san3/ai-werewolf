# D028 突然死・切断・再接続・時刻源・死亡者の情報範囲

## Status

Accepted (2026-08-30) / ユーザー決定（Q31 / Q32 / Q35）＋ Reviewer 決定（Q33 / Q34）

## Context

`sudden_death` は死因の語彙にも霊能者の判定対象にも存在するのに、
発生条件がどこにも書かれていなかった。あわせて Phase 2 に入る前に必要な
切断・再接続・時刻源・死亡者の情報範囲を確定する。

## Decision

### Q31 突然死の発動条件（ユーザー決定）

`rules.sudden_death.enabled`（既定 false）。true のとき、**Day の終了時**に、
その日 `public` へ一度も発言せず CO も宣言しなかった生存者を `sudden_death` で死亡させる。

- Vote へ入る前に解決するため、突然死した者は投票しない
- 判定は Day のみ。Night の沈黙は対象にしない
- 「投票しなかった」は引き金にしない。無投票は棄権として正常に処理される仕様（D023）であり、
  同じ行為を死因にすると矛盾する

**帰結: 勝敗判定の位置が3箇所になる。** Execution 内・Night 内に加え、
Day 終了時の突然死解決直後にも評価する。

### Q32 切断・タイムアウト時の扱い（ユーザー決定）

切断してもゲームは進行し、席も残る。未選択の能力は `no_selection` に従い（D027）、
発言はゼロとして数える。

理由は接続頻度ではなく構造にある。ゲーム状態はサーバだけが持つため接続に依存せず、
また切断で中断する仕様にすると、不利な側が接続を切ることでゲームを壊せてしまう。

サーバから見えるのは「その席が黙っている」ことだけで、
クライアント↔サーバの切断と、クライアント↔LLM の障害は区別できない。
**規則は観測できる事実だけで書き、原因を推測しない。**

実際に頻発するのは後者である（8GB VRAM を9エージェントで共有するため）。
**AIクライアントは LLM が応答しない場合に代替発言を送らず、黙る。**
したがって `sudden_death.enabled: true` のとき、LLM 障害は突然死につながる。
これは意図した挙動であり、既定を false にすることで通常は起こらない。

### Q33 再接続時の本人確認（Reviewer 決定）

Join 時にサーバが接続トークンを発行し、そのプレイヤーへ private に送る。
再接続は必ずトークンで照合し、`player_id` の自己申告を信用しない。
`game.state_sync` は自分の役職・能力結果を含むため、照合を省くと
他プレイヤーの秘匿情報がそのまま漏れる（D001）。

### Q34 時間を進める主体と時刻源（Reviewer 決定）

サーバの単調時計を唯一の時刻源とし、1秒間隔の tick で全ゲームの
`advance_if_due(now)` を呼ぶ。締切は絶対時刻で保持しているため、
tick が遅れても締切は伸びない。クライアントの時計は表示にのみ使う。

### Q35 死亡プレイヤーの情報範囲（ユーザー決定）

`rules.graveyard` を設ける。

```yaml
graveyard:
  view_public: true      # 死亡後も public を閲覧できる
  speak: false           # 墓場での発言（Phase 7）
  reveal_roles: false    # 死亡者に全員の役職を見せる
```

既定は「死亡者に生存者以上の情報を渡さない」。
これを既定にすれば、観戦・墓場を後から足しても情報漏洩の検証項目が変わらない。

## Consequences

- 勝敗判定サービスの呼び出し位置が2箇所から3箇所になる。
  Phase 1.6 の実装は Execution / Night の2箇所のため、突然死の実装時に追加する。
- 突然死は「その日に発言したか」を数える必要があるため、チャット受付ができる
  Phase 2 以降に実装する。Phase 1 では死因の語彙としてのみ存在する。
- 接続トークンはプロトコルの Join / 再接続に関わるため、Phase 2.1 で形を決める。
