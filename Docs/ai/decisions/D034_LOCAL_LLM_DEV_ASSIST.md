# D034 開発補助のローカルLLM

## Status

Accepted (2026-08-30)

## Context

Implementer (Codex) と Reviewer (Claude) の利用枠が実質的なボトルネックになっている。
`spec/CODEX_TOKEN_EFFICIENT_WORKFLOW.md` は会話をリポジトリへ外部化することで
「前回までの会話を理解し直すトークン」を削った。しかし削れていない経路が残る。

テスト出力・実行ログ・`git diff` といった**一度きりの大きな入力**である。
121件のテスト結果や数百行の diff は、要約する価値しかないのに全文が会話へ入る。

一方、Phase 4 ではゲーム内エージェント用にローカルLLM環境が要る。
両者は同じ実行基盤を共有できる。

## Decision

**実行環境はこのリポジトリの外に置く。** `C:\AIagent`。
リポジトリはローカルLLMへ依存しない（Design invariant 10 を維持する）。

- ランタイムは llama.cpp の Windows CUDA ビルド。
  OpenAI 互換 API を `127.0.0.1:8080` で提供する。
- プロファイルを2つ持ち、用途で使い分ける。

  | profile | モデル | 用途 |
  |---|---|---|
  | dev | Qwen3.6-35B-A3B UD-Q4_K_XL | 開発補助。MoE エキスパートを CPU/RAM へ逃がす |
  | game | Qwen3.5-9B Q4_K_M | Phase 4 以降のゲームエージェント。GPU 全載せ |

**使ってよい用途は次の3つに限る。**

1. テスト出力・ログ・diff の圧縮
2. 定型文書（`CURRENT_STATE` 更新、handoff）の草稿
3. 「どこを見るべきか」の絞り込み

**使わない用途。**

- 合否判断。ローカルLLMの出力を根拠に「問題なし」と結論しない
- 仕様の解釈。仕様の最終決定権は人間にある

### 用途1の制約 — 判定値をLLM経由にしない

**成功数・失敗数・エラーの有無は、終了コードと生の最終行から取る。**
LLM に要約させてよいのは失敗の**内容**であって、合否の**値**ではない。

要約器は「121 passed」ともっともらしく書ける。実際にこのプロジェクトでは、
テストが収集段階で落ちて1件も実行されていないのに末尾だけ見ると成功に読める状態が
2回起きている（`jsonschema` が古かったとき、`websockets` が未導入だったとき）。
どちらも `Interrupted: 1 error during collection` であり、
成功数を人が読み違えれば通過してしまう形だった。

### 既定は「使う」。省略には理由が要る

用途1〜3に当たる作業は、**原則としてローカルLLMを通してから会話へ入れる。**
使わなかった場合に理由が要るのであって、使うことに理由は要らない。

判断を迷わせないため、常に通す入力を挙げる。

| 入力 | 目安 | 会話へ入れてよい形 |
|---|---:|---|
| pytest の失敗出力 | 全長 | 失敗したテスト名と原因1行ずつ |
| `git diff`（実装セッションの自己確認） | 200行超 | ファイルごとの変更要旨 |
| `spec/AI_WEREWOLF_CODEX_HANDOFF.md` | 1,952行 | 該当節の抜粋 |
| `spec/CODEX_TOKEN_EFFICIENT_WORKFLOW.md` | 2,096行 | 該当節の抜粋 |
| `REVIEW_INBOX.md` の過去分 | 2,010行 | 対象IDの前後だけ |
| `content.py` など 300行超のファイル | 300行超 | 変更しないなら構造の要約 |

閾値は「読む前に量が分かるもの」に置く。`wc -l` で測ってから決める。

**先にスクリプトで足りないか問う。** OPEN 指摘の抽出は `grep`、
文書の整合は `scripts/check_docs.py`、変更ファイルの一覧は `git diff --stat` で
**トークンを1つも使わずに**済む。LLM へ投げるのはその後である。

**入力量の上限。** dev プロファイルは入力 20,000 トークンで前処理に約60秒かかる。
それを超える入力は、要約を待つより自分で読んだ方が速い場合がある。
渡す前に `--tb=short` や `git diff --stat` や `sed -n` で機械的に削る。

### 用途3の制約 — 順序は決めてよいが対象は減らさない

用途1と2は出力が検証可能である。要約が間違っていればファイルを開いた時点で気付く。
**絞り込みだけは反証できない。** 「ここを見ろ」に従うと、
見なかったものが何だったかは分からないままになる。

したがって、**絞り込みは読む順序を決めてよいが、読む対象を減らしてはいけない。**
diff に含まれるファイルは全部開く。
絞り込みを使ってよいのは「この変更が影響する**既存**コードはどこか」という、
diff の外側に対してだけである。

## Why

節約の本体は会話履歴の圧縮ではなく、**会話へ入る前の圧縮**である。
生ログを貼らずに済ませることが、最も確実で最も大きい。

線引きの理由はレビューの健全性にある。絞り込みを「見なくてよい理由」に使うと、
`AGENTS.md` のレビュー観点を機械的に取りこぼす経路ができる。
45.8 t/s の 35B は判断の補助にはなるが権威ではない。
この線を引かなければ、Implementer と Reviewer を分離した意味が失われる。

なお、機械的に判定できる不変条件は `scripts/check_docs.py` のように
**スクリプトで書けばトークンを消費しない。** LLM へ投げる前に、
まずスクリプトで足りないかを問うこと。

## Consequences

- 実測 (2026-08-30 / RTX 3070 Ti 8GB + i7-12700K + RAM 32GB):

  | profile | 生成 | プロンプト処理 |
  |---|---:|---:|
  | dev | 45.8 t/s | 336 t/s |
  | game | 88.9 t/s | 2948 t/s |

  dev は入力 20,000 トークンで前処理に約60秒かかる。
  それを超える入力は、渡す前に機械的に削ること。
- Phase 4 は同じサーバの game プロファイルを使う。
  Design invariant 9「1つの共有LLMサーバ」を満たす。
- 8GB VRAM を両プロファイルで共有するため、**dev と game は同時に起動できない。**
  ゲームを動かしながら開発補助を使うことはできない。
- game プロファイルの実測値は Q8（9体同時稼働時の生成速度）の初期見積もりになるが、
  9体分の KV キャッシュを載せた実測は Phase 5 で別途行う。
- 環境はリポジトリ外にあり、他のマシンでは再現されない。
  正本は `C:\AIagent\agent\README.md`。リポジトリはその存在を前提にしない。
  再構築用の記録だけを `spec/LOCAL_LLM_SETUP.md` に複製してある。
- **サーバは常駐しない。** 呼び出しが失敗したら圧縮を諦めて生のまま進む。
  ローカルLLMが落ちていることを理由に作業を止めない。
- **使ったかどうかを報告する。** セッション終了時の報告に、
  ローカルLLMを何に使ったか（使わなかったならその理由）を1〜2行入れる。
  客観記録は `C:\AIagent\agent\usage.jsonl` にあり、`tools\usage.py` で読める。
  報告と記録が食い違えば、既定を「使う」にした文言が効いていないということである。
