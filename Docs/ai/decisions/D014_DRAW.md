# D014 引き分け（全員敗北）を勝敗結果の型に含める

## Status

Accepted (2026-08-29) — ユーザー決定「引き分け（全員敗北）は用意してください」

## Context

`decisions/D005` に引き分けの規定が無かった。
これは理論上の話ではなく、13役職の構成で実際に発生する。

```
残り2人（人狼1・猫又1）
→ 猫又を処刑（lynched）
→ 道連れで生存者から1名 = 人狼が死亡（retaliation）
→ 全員死亡
```

D005 は「全死亡処理の解決後に1回判定」なので、この時点で
市民陣営の条件（全人狼死亡）も人狼陣営の条件（市民数 0 ≤ 人狼数 0）も
同時に成立しうる。

## Decision

### 1. 勝敗結果の型に `draw` を含める

```
GameResult
├─ winner_team: TeamId | null
├─ outcome: team_victory | draw
└─ player_results: { player_id: won | lost }
```

**`draw` は「全員敗北」として扱う。** 全員勝利ではない。
`player_results` は全員 `lost` になる。

### 2. 生存者0人は無条件に `draw`

他の勝利条件の成立可否を問わない。生存者が0人になった時点で引き分け。

### 3. 複数陣営の勝利条件が同時成立した場合の優先順位

content 側の設定で明示する。既定の評価順:

```yaml
rules:
  win_evaluation_order:
    - village     # 役職全滅型
    - wolf        # 人数比較型
    - fox         # 便乗型は最後に適用
```

- 生存者0人チェックを**最初に**行う
- 次に上記の順で評価し、最初に成立した陣営を勝者とする
- 最後に便乗型（妖狐）を適用し、成立していれば勝者を差し替える

暗黙の辞書順・定義順に依存しないこと。
順序が未定義の設定はエラーにする。

## Why

- あとから `draw` を足すと、勝敗判定・ログ・リプレイ・将来の戦績/Eloすべてに波及する。
  型に最初から含めるコストはほぼゼロ
- 「全員敗北」と定義したことで、将来レーティングを入れたときの扱いが自明になる
  （全員勝利だとレート計算が破綻する）
- 評価順を設定にしたことで、第三陣営を足しても判定コードを変えずに済む

## Consequences

- `GAME_ENDED` イベントに `outcome` が入る
- 勝利条件評価器は「勝者なし」を返せる必要がある
- Phase 8 で恋人陣営（複数勝者がありうる）を足すとき、
  `winner_team` を単数から複数へ広げる必要が出る。
  **その可能性を型のコメントに残しておく**

## Verification

- 人狼1・猫又1 の状態で猫又を処刑し、道連れで人狼が死んだとき `draw` になる
- `draw` のとき全プレイヤーの結果が `lost` になる
- 生存者0人が他のどの勝利条件よりも優先される
- 評価順の設定を入れ替えると勝者が変わる（順序が実際に効いている）
- 評価順が未定義の設定が起動時にエラーになる
