# D017 available_actions はコアが生成し、フェーズ開始時にプッシュする

Status: Accepted (2026-08-29) / ユーザー設計
「昼、夜の始め、再接続時に死亡者・死亡原因リストを送信」
「能力は夜にしか使わないため、夜の開始時に能力についての情報を送信」
「能力が使用された場合即変更されるのではなく、その後の夜明けで一斉更新」

## Context

マスター仕様 §33 は「サーバはAIへ現在可能な操作を返す」と定めているが、
その計算をどこが行い、いつ送るかが書かれていない。

## Decision

メッセージ形と送信タイミングは `spec/DESIGN.md` §6.3 §9。

要点:

1. 計算はゲームコアが行う（`game.get_available_actions(player_id)`）
2. 死亡情報は差分ではなく全量を送り、生存者はクライアントが導出する
3. 行動情報はそのフェーズの開始時に送る
4. 夜の行動は予約制で、解決は夜明けにまとめて行う
5. 時限で変わるものは終了時刻を渡す
6. プッシュはフェーズ開始時と再接続時の2つだけ

## Why

### 計算をコアに置く理由

同じ問いが2つの形で現れる。

```
検証: この行動は合法か？     → validate_action(player, action) -> bool
列挙: 合法な行動を全部挙げよ → get_available_actions(player) -> list
```

これを別々に手書きすると必ずズレる。制約を宣言的に1箇所へ持ち、両方をそこから導く。

プッシュのタイミングが直すのは「陳腐化」であり、この「不一致」は直らない。
送ったリストが正しいとサーバが保証できるのは、コア自身が作った場合だけである。

### 全量を送る理由

通常更新と再接続が同じメッセージで済み、
差分方式にありがちな「取りこぼしで状態がずれる」事故が起きない。

昼の開始時に前夜の死亡が、夜の開始時に処刑と昼の死亡が届き、過不足なく閉じている。

### 予約制にする理由

使用回数が解決時に消費されるため、対象を選び直しても能力を失わない。
即時反映モデルでは、強欲な人狼が同時噛みを選んで戻しただけで
1回きりの能力を失うバグが必ず出る。

フェーズ途中のプッシュも不要になる。

### 「夜のみ」と固定しない理由

13役職では能力は夜にしか使わないが、参照実装には昼に使う能力がある。
「そのフェーズの開始時」と一般化しておけば、後から足しても設計が変わらない。

### 時限を終了時刻で渡す理由

Reviewer は当初「発言解禁時に追加プッシュが必要」と述べたが撤回する。
終了時刻を渡せばクライアント側でタイマーを持て、サーバのタイマー管理も減る。

## Consequences

ゲームコアに pending actions の概念が必要になる
（`submit_action` と `resolve_pending_actions` を分ける）。
予約は最後の1つだけを保持し、履歴はログに残す。

クライアントの時刻を信用せず、サーバ側でも締切を強制する。
