# D012 死因を第一級の概念とする

Status: Accepted (2026-08-29) / ユーザー決定
「処刑、噛む、道連れというのを別の死因として用意するのが丸い」
「公開死因は処刑、昼の処刑以外での死亡、夜の死亡（死亡理由によらず全部同じ）」

## Context

マスター仕様の `PLAYER_DIED` は死因を持たない。
しかし死因で挙動が変わる役職が既にある（猫又・霊能者）。
場当たり的に扱うと、役職を足すたびにコアへ分岐が増える。

## Decision

`DeathCause` を列挙として定義し、content から読む。
公開死因は3値のみとし、**死亡解決時のフェーズから導出する。**
詳細は `spec/DESIGN.md` §7.2 §7.3。

## Why

### 内部死因ごとの対応表を持たない理由

呪殺された妖狐が襲撃死と区別できてしまうと、村側は
「呪殺が起きた＝あの占い師は本物で妖狐を引いた」と即座に確定でき、
妖狐と占い師の駆け引きが成立しなくなる。

マスキングを対応表で持つと、content が新しい死因を追加したときに
追記漏れがそのまま漏洩になる。役職を YAML だけで追加できる方針（D009）と
組み合わさると、**Python を触らない追加で漏洩が起きる**。

フェーズから導出すれば、どんな死因が増えても自動的にマスクされる。
漏れうる箇所そのものが消える。

死んだ時刻はプレイヤーから観測可能なので、昼夜の区別を公開しても情報は増えない。

### その他

- 死因で分岐する役職を content だけで表現できる
- 道連れを独立した死因にしたことで死亡連鎖が止まる（D011）

## Consequences

クライアントへ送る死亡イベントには公開死因のみを入れる。
Phase 2 のプロトコル設計時、死亡イベントの型は
サーバ内部用とクライアント向けの2種類になる。
