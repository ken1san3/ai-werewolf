# D049 送信待ちの隔離・入室認可・再送履歴の保持範囲

## Status

Accepted (2026-09-01、R-20260831-72〜74 の修正)

## Context

D047 のサーバ全体のロックがネットワーク送信完了まで保持され、遅い接続が全ゲームの
tick を止めていた。また全量 sync 自体を再送履歴へ複製していた。初回入室認可は
ユーザーが D048 で決定した。

## Decision

- D047 の送信ロック方針を置換する。dispatch lock 内で行うのは core の処理、
  snapshot の捕捉、宛先ごとの封筒・seq の確定、キューへの追加までとする。
  送信は接続ごとの FIFO キューを専用タスクが取り出し、send lock の下で行う。
  tick・別接続・別ゲームはその I/O 完了を待たない。
- 接続ごとの送信待ちを `max_pending_messages`（既定256件、最小2件）で制限する。
  上限到達時はその接続だけを1013で閉じ、再接続で回復させる。置換・切断・終了時は
  古い writer とキューを破棄する。ネットワーク close も dispatch lock の外で行う。
- D048 の入室トークンは `GameRegistry` がゲーム登録時に全席へ乱数で発行する。
  起動側へ渡す API は `entry_tokens_for(game_id)`。ゲームの通信やログへ一覧を出さない。
  `session.join.payload.entry_token` から席を引き、成功時に消費する。
  再接続用 `connection_token` は別に発行し、2種類を照合する表も分ける。
- 再送履歴は `replay_history_limit`（既定128件）までとし、古い順に捨てる。
  Resume の `last_seq` までの受領済み項目も破棄する。`game.state_sync` は履歴に入れず、
  生成した時点でそれ以前の履歴を置き換える。
- 保持範囲外、または失われた snapshot より前のカーソルでは、不完全な replay を送らず
  新しい resume 応答と全量 sync で復元する。保持範囲内の replay は元の seq と封筒を保つ。
  sync が新しい現在地であることは D047 と同じ。コアの許可済み履歴は1つだけ保持し、
  接続回数に比例した snapshot の複製は作らない。

## Consequences

- 上限値は transport の資源制限で、ゲームルールには追加しない。コンストラクタで変更できる。
- 入室トークンを配る UI・運用は D048 どおり対象外。Phase 2.6 の起動側は上記 API を使う。
- 1秒の遅延送信中の複数ゲームの tick・他接続、送信中の接続置換、キュー飽和、
  トークンの欠落・混同・再使用、30回の再接続と履歴上限を回帰テストで固定する。
- DESIGN.md は変更しない。D047 の当初の実装判断は履歴として残す。
