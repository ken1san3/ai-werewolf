# D031 プロトコルの版と順序 / チャネルの実装範囲 / Modifier は1人1つ

## Status

Accepted (2026-08-30) / Q6・Q11 は Reviewer 決定、Q24 はユーザー決定

## Context

Phase 2.1 に入る前に、後から変えると全メッセージの形が変わる決定
（Q6）と、送信経路の実装範囲（Q11）を確定する必要があった。
あわせて Phase 8 まで先送りにしていた Modifier の属性衝突（Q24）を、
機構を増やさずに閉じる。

## Decision

### Q6 プロトコルのバージョンと順序（Reviewer 決定）

- `protocol_version` は接続時のハンドシェイクで交換し、メジャー不一致は接続拒否。
  **そのうえで全メッセージにも保持する。** イベントログがそのまま再生の入力になるため
  （D013）、記録された1行だけを見て解釈できる必要がある。
  冗長さより、古いログを読めることを優先する。
- `seq` は**サーバ→クライアントのイベントにのみ**付ける。1から単調増加し、欠番を作らない。
  クライアント→サーバの要求には付けない。
  **採番単位はプレイヤー単位（D035 で改定）。** 当初はゲーム単位としていたが、
  宛先の異なる private イベントが混ざると各クライアントの受信列に欠番が出て、
  取りこぼし検出という `seq` の目的が果たせないため。
- 再接続時はクライアントが受信済みの最終 `seq` を送り、サーバはそれより後を送る。
- `seq` は取りこぼし検出のためであり、**順序保証の根拠にはしない。**
  権威はサーバの状態であって、クライアントが並べ替えた結果ではない。

### Q11 チャットチャネルの実装範囲（Reviewer 決定）

| チャネル | 送信の実装 |
|---|---|
| `public` / `wolf` / `fox` / `system` | Phase 2 |
| `lover` | Phase 8（Modifier と同時） |
| `graveyard` / `spectator` | Phase 7 |

チャネル定義は全て content に存在済みで、決めたのは送信経路を作る時期だけである。

本人だけへの送信はチャネルではなく、イベントの可視性
（`PRIVATE` ＋ `recipient_player_id`）で行う。
`private:` のようなチャネルIDは registry に存在しない。

### Q24 複数 Modifier による属性の衝突（ユーザー決定）

**1人のプレイヤーが同時に持てる Modifier は最大1つ。** 二重付与は起動時・付与時に拒否する。

これで同一属性を2つの Modifier が異なる値で上書きする状態が**構造的に発生しない。**
priority も付与順の規則も要らない。

## Why

Q24 に優先順位の機構を入れると、`overrides` の解決順・`win_condition` の
`mode` との相互作用・Modifier ごとの priority という3つの規則が同時に増える。
そのすべては「2つ同時に付く」ことだけを前提にしている。前提を落とせば規則も消える。

## Consequences

- `Player.modifiers` は要素数0か1になる。tuple のままにしておき、
  上限は付与の境界で検査する。将来2つ以上を許すなら、それは Q24 の再オープンであり、
  優先順位の規則を決めてからにする。
- `Modifier.exclusions` は役目を失う。上限1のもとでは、既存の Modifier が
  あらゆる新規付与を等しく拒否するため、個別の排他宣言に意味がない。
  Phase 8 の Modifier 実装時に削除する。
- 恋人は「2人に1つずつ付く」であって「1人に2つ付く」ではないため、この上限と衝突しない。

## Verification

- ハンドシェイクのメジャー不一致で接続が拒否される。
- イベントの `seq` が1から欠番なく増える。再接続で最終 `seq` 以降だけが届く。
- 2つ目の Modifier を付与しようとするとエラーになる。
- Phase 2 で `graveyard` / `spectator` / `lover` へ送信する経路が存在しない。
