# D053 Reviewer を2体にする

## Status

Accepted（ユーザー決定 2026-09-02。Q39 の回答）

## Context

R-20260901-97 は Sol が起票した High の実バグで、**Claude のレビューが見落としたもの**
だった。独立した2つ目の目が実際に機能した。
一方で Claude のトークン消費は大きく、レビューを1体に集中させる必要は無い。

## Decision

**実行体制（ユーザー説明 2026-09-02）:**

| レーン | model | 備考 |
|---|---|---|
| 通常レビュー | Claude, Sol | どちらへ送ってもよい |
| 深掘りレビュー | Sol | |
| 詳細設計 | Sol | |
| 実装 | Luna | |

**Sol の3レーンはそれぞれ別のチャットで動く。** 文脈を共有しない。
したがって設計を書いた Sol と、それをレビューする Sol は、
**互いの思考過程を持たない独立したセッション**である。

どのレーンでも、起票先は `REVIEW_INBOX.md`、ID・severity・状態の規約は同じ。
`CURRENT_STATE.md` の Latest Review / Test Status / Next Task を更新し、
報告は「次に誰へ何を送るか」で締める（RUNBOOK §2.4）。

**1つだけ担当を固定する。Sol が書いた詳細設計の `Status: APPROVED` は Claude が付ける。**
逆に Claude が書いた設計は Sol が承認する。

## Why

チャットが別なので**文脈の独立性は確保されている。** 残る差は model の差だけである。

そこが問題になる。R-97 は「Claude が読んで気づかなかったものに Sol が気づいた」事例、
つまり **model が違うから見つかった**指摘だった。同じ model は同じところを見落とす。
Design Gate の承認は「その後の実装レビューすべての前提」を固定する一点であり、
ここだけは model を変える価値が費用を上回る。設計文書1枚を読む費用は、
実装レビュー1回よりずっと小さい。

逆に、通常レビューと深掘りレビューを Sol へ寄せることは妨げない。
それが2体化の目的である。

## Consequences

- ユーザーは「レビューして」を Claude と Sol のどちらへ送ってもよい
- **Sol が設計した Phase の `DESIGN REVIEW: APPROVED` だけは Claude へ回す。**
  誰が書いたかは `_DESIGN.md` から辿れる必要がある
- 重複IDの機械検査が `REVIEW_INBOX.md` に閉じている（R-20260902-101）。
  同じ日に複数レーンが起票するため、アーカイブまで広げる必要がある
- `REVIEW_INBOX.md` と `CURRENT_STATE.md` は複数レーンが書く。
  同時編集は衝突するので、1セッション1体を前提とする
- 通常レビューと深掘りレビューの境界は未定義（Q40）
