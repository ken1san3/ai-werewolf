# D013 ログとリプレイの方針 — 乱数の完全再現を目標にしない

## Status

Accepted (2026-08-29) — ユーザー決定
「乱数の再現性はあまり求めません。それを言うならAIモデルも完全再現をさせるべきですが、
それは難しいので。というわけでログを残して見返せるようにしてください」

## Context

`OPEN_QUESTIONS.md` Q18 で、Reviewer は
「単一シードからの完全再現」を推奨した。**却下された。**

却下の理由は一貫している。Phase 4 以降は LLM がプレイヤーになるが、
LLM の出力は温度・バッチ・バックエンドのバージョンによって変わる。
ゲームコアだけ完全再現できても、**試合全体は再現できない**。
一方だけに実装コストを払う意味が薄い。

## Decision

### 1. 「再シミュレーションによる再現」を目標にしない

同じシードから同じ試合を再生成する仕組みは作らない。

### 2. リプレイは**イベントログの再生**とする

マスター仕様 §25 が求めているのは
「イベントログからゲーム経過を確認できること」であり、再計算ではない。

```
リプレイ = 記録済みイベントを時系列に流し直す
         ≠ 同じ入力から再計算する
```

このため、**ランダムな結果はすべてイベントとして記録する。**

| ランダム要素 | 記録するイベント |
|---|---|
| 役職配布 | `ROLE_ASSIGNED`（誰がどの役職か） |
| 役職欠け | `ROLE_MISSING_APPLIED` |
| 初日ランダム白 | `INITIAL_INSPECT_GRANTED`（対象と結果） |
| 投票同数のランダム処刑 | `TIE_RESOLVED_RANDOM`（選ばれた対象） |
| 猫又の道連れ抽選 | `RETALIATION_TARGET_SELECTED`（選ばれた対象） |

**「乱数を引いた」ではなく「何が選ばれたか」を記録する。**
これならリプレイ側は乱数を一切扱わない。

### 3. ゲーム状態のスナップショットではなくイベント列を保存する

```
Event 1
Event 2
Event 3
...
```

任意の時点の状態は、先頭からイベントを適用すれば復元できる。
完全な Event Sourcing までは要求しないが、
**イベントだけでゲーム経過を追えること**を満たす。

### 4. ログは公開ログと秘匿ログに分離する（旧 Q7 の回答）

マスター仕様 §24 は全ログの保存を求め、§27 は情報漏洩を禁じている。
同一ファイルに書くと、観戦UI・リプレイ共有・デバッグ共有で漏れる。

```
logs/<game_id>/
├─ public.jsonl     全員が見てよいイベント（公開チャット、公開死亡、投票結果）
├─ private.jsonl    役職・秘密チャット・能力使用・内部死因
└─ ai.jsonl         LLM の入出力・レイテンシ・内部判断（Phase 4 以降）
```

- 観戦・リプレイ配布では `public.jsonl` のみを使う
- ゲーム終了後の全体公開は、設定で明示的に有効化したときのみ
- **`private.jsonl` の内容を進行中のクライアントへ送らない**

### 5. ログの最低保存項目

```
game_id
開始日時 / 終了日時
game config（ルール設定の実効値）
player config
役職配布結果
全公開チャット
秘密チャット（private側）
投票（誰が誰へ）
能力使用と結果
ゲームイベント
死因（内部 / 公開の両方。private側に内部死因）
勝敗と各プレイヤーの勝敗
AI内部判断・LLM入出力・レイテンシ（ai側、Phase 4以降）
```

### 6. ただしテストでは RNG を注入可能にする

試合の完全再現は目標にしないが、
**ユニットテストが乱数で不安定になるのは別問題**である。

- 乱数は `game.rng` 経由に統一する（モジュールレベルの `random` 直接使用は禁止）
- テストは固定 RNG またはモック RNG を注入できること
- これは「試合の再現」ではなく「テストの安定性」のための要件

## Why

- LLM を含む試合全体の再現は現実的でない。
  ゲームコアだけの再現に実装コストを払う費用対効果が低い
- イベントログ方式なら、**乱数の実装を変えても過去のリプレイが壊れない**
- 公開/秘匿の分離は、D012（死因のマスキング）と同じ原則の適用先違いであり、
  実装を1箇所にまとめられる

## Consequences

- ランダムな選択を行う Effect は、必ず結果をイベントとして発行する。
  「静かにランダムを引いて状態だけ変える」実装はレビューで指摘対象
- リプレイ実装は乱数を持たない（読むだけ）
- ログ出力先が3系統になる。書き分けを間違えると漏洩なので、
  **イベントに公開範囲を持たせ、ログ出力側が振り分ける**形にする
  （呼び出し側が出力先を選ぶ設計にしない）

## Verification

- 1試合を実行し、`public.jsonl` だけでゲーム経過を追える
- `private.jsonl` に含まれる情報が `public.jsonl` に現れない
- 内部死因 `cursed` が `public.jsonl` に現れない
- ランダムな選択（道連れ対象・同数処刑）の結果がイベントとして残っている
- 固定 RNG を注入したテストが安定して通る
- モジュールレベルの `random` を直接呼んでいる箇所が存在しない（静的チェック）
