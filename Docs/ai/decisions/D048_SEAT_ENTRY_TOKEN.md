# D048 席ごとの入室トークンで Join を認可する

## Status

Accepted (2026-08-31) / ユーザー決定（Q37 クローズ）

## Context

`session.join` は `player_id` の自己申告だけで席に着けた。Phase 2.5 で
`game.state_sync` を Join 直後に返すようにしたため、**認証を持たない接続が
任意の席の役職を読める**状態になった（R-20260831-73）。

DESIGN §9.1 の本人確認は resume にしか無く、初回 Join の認可方式は
Q37 として未決のままだった。

## Decision

**ロビー作成時に、サーバが席ごとの入室トークンを発行する。**
`session.join` は `player_id` ではなく入室トークンを受け取り、
サーバがトークンから席を引く。`player_id` の自己申告は受け付けない。

- 入室トークンは席の識別子であり、資格情報である。乱数から作る
- Join が成功すると、これまでどおり**接続トークン**を private に返す。
  以降の再接続は接続トークンで照合する（既存の仕組みを変えない）
- 入室トークンは1つの席につき1回だけ使える。使用済みの席への Join は拒否する
- 拒否は理由イベントを返さず接続を閉じる（未認証接続に `seq` を振れないため。
  D035 と同じ扱い）

**入室トークンをどう配るかは、この決定の外側である。** Phase 7 の UI で
リンクを配る、手で渡す、といった運用の話であり、サーバは
「正しいトークンを持つ接続だけが席に着ける」ことだけを保証する。

### 採用しなかった案

- **ロビー作成者が割り当てる。** ホストの認証とロビーの状態機械を
  先に作る必要があり、Phase 2 の範囲を超える。将来この方式に移る場合も、
  ホストが配るのは入室トークンになるため、本決定と両立する
- **局内限定のまま保留する。** 未決事項を1つ残したまま Phase 3 以降へ進むと、
  AIクライアントの接続方式がその前提で固まる。決めるなら今が安い

## Consequences

- `session.join` の client schema が変わる。`player_id` を送らせない
- ゲーム生成時に席ごとの入室トークンを作り、外部（ロビー / 起動スクリプト /
  テスト）へ渡す経路が要る。`GameRegistry` かゲーム生成 API のどちらが持つかは実装で決める
- 既存テストの Join はすべて入室トークン経由になる
- 接続トークン（再接続用）と入室トークン（初回用）の2種類になる。
  名前を明確に分けること。混ざると R-73 と同じ穴が戻る
- DESIGN §9.1 に Join 側の本人確認を、§9.3 に「途中参加」が
  認可済みの席の初回接続を指すことを明記する（Reviewer）

## Verification

- 入室トークンを持たない `session.join` は席に着けず、`game.state_sync` を受け取らない
- 他人の `player_id` を知っていても、その席へは入れない
- 正しい入室トークンでの Join は接続トークンとスナップショットを受け取る
- 同じ入室トークンでの2回目の Join は拒否される
- 再接続は従来どおり接続トークンで行え、入室トークンでは再接続できない
